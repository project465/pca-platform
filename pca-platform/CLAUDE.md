# 단체 PCA 플랫폼

이 파일은 Claude가 매 세션 시작할 때 읽는 프로젝트 설명서다.
새 결정이 생기면 여기에 추가한다.

---

## 무엇을 만드는가

대학 **전 학과**에 파는 진로 지표 검사 플랫폼. (공과계열 한정이라는 서술은
옛 것이다 — 2026-09-09 총괄 확인)

학생이 검사를 보면 **그 전공으로 갈 수 있는 직무 분야**를 알려주고,
그 직무에 필요한 **역량**과 채우기 위해 들어야 할 **과목**까지 제시한다.

- 응시 대상: 대학 재학생
- 계약 주체: 학과 (또는 취업지원처)
- 첫 대상 학과: 기계공학과
- 참고 모델: 르네상스러닝 (검사 → 리포트 → 처방 구조가 동일)

## 확정된 결정

| 항목 | 결정 |
|---|---|
| 계정 발급 | 계약 후 관리자가 발급. 셀프 가입 아님 |
| 계정 단위 | 기관 단위 + 개인 단위 둘 다 (개인은 나중) |
| 과금 | 계약 좌석(응시권) 차감. 구독/크레딧 아님 |
| 출제 방식 | 고정 문항. 적응형(CAT) 아님 |
| 중간 저장 | 문항마다 즉시 저장, 이어보기 지원 |
| 응시 자격 | 명단 기반 **또는** 단체 전용 링크. 둘 다 지원한다 |
| 단체 도입 | 홈페이지 신청 → 운영자 승인 → 전용 링크 발급. 승인 없이는 아무것도 생기지 않는다 |
| 메일 | SMTP 로만 말한다. 공급자를 코드에 박지 않는다. 비밀번호는 메일로 보내지 않고 설정 링크를 보낸다 |
| 결과 공개 | 학과 담당자 승인 후 공개 |
| 도메인 | 국가별 별도 도메인 |
| 다국어 | translations 테이블에 행으로 저장 |

| 소개 사이트 | 나라별로 만든다. 글로벌(영어)·한국 먼저, 카자흐스탄·터키는 다음 |

## 설계 원칙 (어기면 안 됨)

**1. 로그인 주체는 users 하나다.**
기관 소속 학생이든 개인회원이든 전부 `users`에 들어간다.
소속은 `memberships`로 연결한다. 회원 테이블을 기관용/개인용으로 나누지 않는다.

**2. 사람이 읽는 이름은 전부 translations에 모은다.**
`name_ko`, `name_en` 같은 컬럼을 만들지 않는다.
나라를 추가할 때 컬럼이 아니라 행이 늘어나야 한다.

**3. 채점 산식은 코드가 아니라 데이터다.**
직무 적합도는 `scoring_weights` 테이블의 가중치로 계산한다.
산식을 코드에 하드코딩하면 학과별·국가별로 다르게 줄 수 없고, 바꿀 때마다 배포해야 한다.

**4. 검사 문항은 수정하지 않고 버전을 올린다.**
`instruments.version`. 작년 응시자의 결과가 올해 문항 수정으로 바뀌면 안 된다.

**5. 마케팅 사이트와 검사 플랫폼은 별개다.**
국가별 도메인은 소개·영업용. 학생이 검사를 보고 결과를 받는 플랫폼은 전 세계 하나다.
그래야 국가 간 비교가 가능하고, 그게 이 서비스의 핵심 자산이다.

**운영사 관리자**
0. 도입 신청 검토와 승인 → `/admin/applications`
1. 기관 목록
2. 계약·응시권 등록
3. 검사 문항 관리
4. 매핑 데이터 관리
5. 전체 응시 현황

**학과 담당자**
5.5. 전용 링크 관리 (복사·회수·발급) → `/org`
6. 회차 생성
7. 명단 업로드 및 계정 일괄 발급
8. 응시 진행 현황
9. 단체 리포트 → `mockups/03_group_report.html`

**학생**
10. 로그인
11. 검사 응시 → `mockups/01_test_screen.html`
12. 결과지 → `mockups/02_student_report.html`

소개 사이트는 만든다. (2026-09-04 결정 변경. 그전에는 MVP에서 뺐었다.)
영업은 여전히 대면으로 하되, 나라별 도메인에 소개 사이트를 두고 문의를 받는다.
검사 플랫폼과는 코드가 분리돼 있다 — `marketing/` 이 소개 사이트고, `src/` 가 플랫폼이다.

소개 사이트는 한 코드베이스에서 나라별 원고만 갈아 끼운다.

```
SITE=global npm run build   →  영어판
SITE=kr     npm run build   →  한국어판
SITE=kz / SITE=tr           →  원고 파일만 추가하면 된다
```

각 사이트의 로그인 버튼은 전부 같은 플랫폼 한 곳을 가리킨다 (설계 원칙 5).

## 개발 순서

1. **계정** — users, organizations, memberships, 로그인, 비밀번호 재설정, 관리자에서 기관 생성
2. **계약과 회차** — contracts, seats, test_sessions, 명단 엑셀 업로드로 계정 일괄 생성
3. **응시** — 응시 화면, responses 저장, 이어보기 ✅ (2026-09-09)
   문항은 `scripts/load-instrument.ts` 로 파일에서 넣는다. 텍스트는
   translations 의 행이다. 회차는 담당자가 `/org` 에서 연다.
4. **채점과 결과** — scoring_weights 적용, 결과지, 단체 리포트
   결과지 화면은 만들어 두었다 (2026-09-09). 값이 들어오면 그리는 껍데기이고,
   채점 산식이 정해져 job_fit_scores·competency_levels 가 채워지면 그대로
   그려진다. 결과 공개는 담당자가 /org 에서 누른다.
   단체 리포트도 만들어 두었다 — /org/report/<sessionId>. 집계만 보여주고
   개인은 짚지 않는다. 남은 것은 채점 산식 하나다.

3단계까지는 채점 산식 없이 진행 가능하다.

## 기술 스택

- Next.js (App Router) + TypeScript
- PostgreSQL
- 인증은 직접 구현하지 말고 검증된 라이브러리 사용
- 파일 저장은 S3 호환 스토리지
- 브라우저 저장소(localStorage 등)에 응답을 보관하지 않는다. 서버에 저장한다.

## 앵커사업 (2026, 교육부)

한국판 소개 사이트의 대학 대상 논지는 이 정책에 맞춘다.

- 2025년 출범한 **라이즈(RISE, 지역혁신중심 대학지원체계)** 가 2026년
  **‘지역성장 인재양성체계(앵커)’** 로 명칭·체계가 재정립됐다
- 목표는 ‘지역인재육성-취·창업-정주’ 선순환 생태계와 5극3특 균형성장
- 2026년 예산 21,403억 원(’25년 19,410억). 이 중 **약 4,000억 원을 성과평가
  인센티브 재원**으로 써 지방정부별로 차등 지원한다. 초광역 단위 사업 2,000억 원
- 평가는 ① 예산 나눠먹기가 없었는지 ② 지방정부-대학 소통 ③ **학생·인재에 대한
  충분한 고려가 있었는지** 를 집중 점검한다. 17개 지방정부 평가 결과는 공개된다
- 시도 중점 사항이 ‘대학 선정·사업비 교부’ 에서 **‘학생 중심 지원 강화’** 로 옮겨갔다
- 성과지표 예시에 **지역정주 취업률(졸업 후 해당 시도 내 취업자 비율)** 과
  **지역 내 유지취업률** 이 있다. 교육부 평가 전 지방정부는 대학 대상 자체평가를 한다

**PCA 가 댈 수 있는 것과 없는 것을 섞지 않는다.**
지역정주 취업률은 졸업 후 취업 통계로 확정되는 지표이므로 PCA 가 산출한다고 쓰지 않는다.
PCA 가 대는 것은 학생 체감의 증거(개인 15–20페이지 전략서)와 정주로 가는 과정
데이터(지역기업 매칭률·정주 관심)다.

출처: 교육부 「지역성장 인재양성체계(앵커) 추진방안」 보도자료 (2026.4.2) 및 별첨 추진방안

**플랫폼 스펙과 어긋나는 부분이 있다.** 이 파일의 개발 순서와 스키마는
"역량 갭 → 개설 과목 처방"을 전제하는데, 제안서에는 그 개념이 없고
"자격·프로젝트·포트폴리오·면접·창업·지역기업"으로 이어진다.
이 대목은 아직 정해지지 않았다.

**응시 자격은 정해졌다 (2026-09-09).** 이 파일은 명단 기반이었고 제안서는
전용 링크 발급이었는데, 둘 다 지원하기로 했다. 명단 업로드는 그대로 두고
전용 링크를 더한다. 링크는 열린 가입이 아니다 — 운영자가 승인해야 생기고,
계약한 좌석 수만큼만 등록되며, 회수·만료가 있다. 그래서 "셀프 가입 아님"
결정과 어긋나지 않는다. `db/schema.sql` 의 `org_applications`·`org_links` 참고.

## 정산 방식은 정해졌다 (2026-09-09)

선불만 있던 것에 **건당 정산**을 더한다. 둘 다 지원한다.

| | 선불 (prepaid) | 건당 (per_use) |
|---|---|---|
| 언제 산다 | 계약할 때 응시권을 미리 | 사지 않는다 |
| 무엇이 막는다 | 남은 좌석 수 | 발주처가 정한 건수 상한 (없을 수도 있다) |
| 청구 | 계약 시점 | 달마다, 나간 건수만큼 |
| 주로 쓰는 곳 | 학과 자체 예산 | 대학 산학협력단, 지역 일자리·경제진흥원, 고용노동부 위탁사업 |

**한 건 = 제출을 마친 응시 하나다.** 시작만 하고 만 것은 세지 않는다.
제공되지 않은 것을 청구하면 검수에서 잘리고, 잘리는 것보다 애초에
청구하지 않는 편이 낫다. 이 기준을 바꾸려면 `db/schema.sql` 13절과
`src/lib/billing.ts` 를 함께 고친다.

단가는 발생 시점의 값을 `billing_events` 행에 박아 둔다. 나중에 단가를
고쳐도 지난 달 청구서가 따라 바뀌지 않게 하기 위해서다.

**기관 계약에는 PG(카드결제)가 필요 없다.** 공공기관과 대학은 카드로
실시간 결제하지 않고 세금계산서로 후불 정산한다. PG 는 개인 진단(B2C)을
열 때 필요한 것이고, 그때도 사업자등록과 통신판매업 신고가 먼저다.

## 총괄 확정 사항 (2026-09-09 저녁)

원고를 고칠 때 이 절을 먼저 본다. 여기 적힌 것과 어긋나는 문장은 옛 것이다.

### R015 · 검사 구조는 개편 중이다 — 숫자를 박지 말 것

새 용어: **계열(큰 묶음) → 분야(=전공: 경영·법·간호…) → 영역(분야 안의
직무영역, 수는 분야마다 다름)**.

**계열별 분야 목록과 분야별 영역 수는 아직 회의 중이다.** 원고에 숫자를
적지 않는다. 예전 원고의 "직무 영역 10개(경영·전략, 인사·조직 …)" 는 사실
**경영학과 하나의 영역 목록**이었다. 전 학과에 파는 원고에 한 학과의 목록을
전체인 것처럼 적고 있었다.

## 카자흐스탄판 (2026-09-09)

소개 사이트가 셋이 됐다. `SITE=kz`, 도메인 `pca.kz`, 언어 `kk`.

**결을 일부러 다르게 했다.** 글로벌·한국판은 흰 종이에 잉크와 금색이고,
카자흐스탄판은 어두운 바탕에 하늘빛이다(`theme: "steppe"`). 같은 회사가 낸
것이되 같은 페이지를 번역만 한 것처럼 보이지 않아야 한다는 요청이었다.
다만 **결과지는 어느 판에서든 흰 문서**다 — 그것이 브랜드 규칙이다.

원고에서 지킨 것:

- **앵커사업 논지를 옮겨오지 않았다.** 한국 교육부 정책이다. 카자흐스탄
  정책 수치는 확인한 것이 없으므로 쓰지 않는다. 대신 "무엇이 공유되고
  무엇을 여기서 채우는가"(localisation)로 간다
- **지역 기업 수치(184곳·144곳)는 한국 대전의 예로만 쓴다.** 화면에도
  "Корея, Тэджон мысалы" 라고 적어 두었다. 카자흐스탄 수치는 파트너
  대학과 함께 만들기 전에는 없다
- **파트너 이름을 적지 않았다.** 한국판에는 대학·기업 이름이 있지만
  카자흐스탄에는 아직 아무도 없다

**카자흐어 원고는 원어민 검수를 받지 않았다.** 배포 전에 반드시 받아야 한다.
러시아어판이 따로 필요할 수 있다 — 카자흐스탄 대학은 두 언어를 함께 쓴다.

곁들여 고친 것: 화면에 박혀 있던 문구를 전부 원고의 `ui` 블록으로 옮겼다.
나라가 둘일 때는 `kr ? "…" : "…"` 로 버틸 수 있었지만 셋이 되는 순간 새
나라가 영어판 문구를 뒤집어쓴다.
