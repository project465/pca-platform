# 배재대 Canary 의 P0 셋

운영 Canary 를 사람이 끝까지 밟고 남은 것을 두 회차에 걸쳐 다뤘다. 학생
신분과 종이와 작업공간과 담당자 집계다. 범위는 그 넷뿐이고 Core 와 문항과
채점과 결과 모델과 등록부와 학생 공개 상태는 한 줄도 건드리지 않았다.

| | 운영에서 사람이 본 것 | 이 회차 |
|---|---|---|
| 1 | 발급한 계정과 응시한 계정이 갈렸다 | **원인을 찾아 고쳤다** |
| 2 | 학과 선택 → 검사 시작 PASS | 건드리지 않았다 |
| 3 | PRO 제출 → 경영 결과 PASS | 건드리지 않았다 |
| 4 | PDF FAIL | 원인 미확정. 운영에서 읽는 자리를 만들었다 |
| 5 | 담당자 집계 미확인 | 로컬 PASS. 운영 확인은 사람이 한다 |
| 6 | `/me` FAIL | **원인을 찾아 고쳤다** |

판정은 `PCU CANARY BLOCKED` 를 그대로 둔다. 셋 가운데 운영에서 PASS 를
받은 것이 아직 없다.


## P0-1 발급한 계정과 응시한 계정이 갈렸다

운영 `pcu:diag` 가 적어 준 것이 이렇다. 응시한 사람은 아이디가 없고
`campus_students` 줄이 없는데 그 응시에는 학교와 학과가 적혀 있다. 학교가
`pcu:students` 로 발급한 계정은 따로 있다. 그러면 담당자 화면은 그 응시를
그 학과의 학생으로 세고, **발급받은 학생은 아직 아무것도 하지 않은
상태다.** 그리고 그 사람은 학교 계약으로 PRO 한 벌을 받았다.

### 왜 갈렸는가

학교 쪽 `검사 시작` 이 **로그인했는지만** 보고 보냈다.

```ts
const who = await currentUser();
if (!who) redirect(학교 로그인);
redirect("/v3/start");          // 누구든 지나간다
```

그래서 **이미 다른 계정으로 들어와 있던 사람**이 그 단추를 누르면 그
사람의 응시가 열리고, 쿠키에 적힌 학교와 학과가 그 줄에 적히고 등급이
PRO 로 섰다. 응시를 여는 자리도 쿠키를 그대로 믿었다: 그 사람이 그 학교의
학생인지 묻는 줄이 없었다.

**학교 로그인이 그 상태를 고칠 수 없었다.** 그 쪽은 세션이 있으면 그대로
돌려보냈으므로, 실습실 PC 처럼 앞사람의 세션이 남아 있는 자리에서는
**학교 계정으로 바꿀 길이 아예 없었다.** 발급한 계정으로 들어갈 수 없는데
학과 쪽 단추는 눌리는 상태였다.

적어 둔 다섯 가지 가운데 확정한 것은 첫째다. 나머지는 이렇게 가른다.
학교 로그인 뒤에 세션이 유지되는 문제는 아니다(학교 로그인은 그 자리에서
세션을 바꾼다). Campus 로그인이 기존 B2C 계정을 고르는 문제도 아니다
(고르는 자리는 아이디 하나뿐이다). 다만 **아이디와 이메일이 같은 글자일 때
어느 줄이 오는지가 정해지지 않은 자리**가 있었고, 그것은 함께 닫았다.

### 고친 자리 셋

**학교 맥락은 그 학교의 학생에게만 적는다.** 쿠키가 들고 온 학과를 믿지
않고 **등록된 줄**을 쓴다(규격 §7). 맞추는 자리는 쿠키가 들어오는
경계 하나다(`/v3/start` 의 서버 액션). 학생이 아니면 맥락을 버리고 일반
B2C 응시를 연다: 그 사람은 개인 회원이고, 비슷한 자리로 짐작해 학교에
넣지 않는다.

**학과 쪽 `검사 시작` 이 신분을 본다.** 그 학교의 학생이 아니면 학교
로그인으로 보낸다. 거기가 앞사람의 세션을 학교 계정으로 바꾸는 자리다.

**다른 계정이 열려 있어도 학교 로그인이 닫히지 않는다.** 그 학교의
학생으로 들어와 있을 때만 돌려보낸다. 다른 계정이면 폼을 세우고 지금
다른 계정으로 로그인되어 있다는 것을 한 줄로 적는다. **누구인지는 적지
않는다.**

**아이디가 이메일보다 먼저다.** `login_id = $1 OR lower(email) = lower($1)`
에 차례가 없어서, 한 사람의 아이디와 다른 사람의 이메일이 같은 글자일 때
어느 줄이 오는지 정해지지 않았다. 학교가 발급한 학번으로 들어온 사람이
남의 계정으로 들어앉는 길이고, 그 응시는 되돌릴 수 없다.

### 되돌려 보고 걸리는 것까지 확인했다

`npm run pcu:campus` 에 네 줄을 더했다.

```
통과  개인 계정으로 들어와 있으면 학교 응시로 보내지 않는다 — /campus/pcu/login
통과  다른 세션이 있어도 학교 로그인이 열린다
통과  쿠키를 들고 바로 쳐도 학교 맥락이 적히지 않는다 — 학교 없음 · BASIC · ME_CORE_V3
통과  발급한 계정이 응시한 계정이다 — 발급 2099 · 응시 2099
```

**응시가 열리지 않으면 그 줄이 아무것도 말하지 않는다.** 처음에는 이용권이
없어 응시가 안 열렸고, 그 상태로 `학교 맥락이 없다` 가 통과했다. 이용권을
주어 응시를 실제로 열고, 열리지 않으면 걸리게 고쳤다.

### 운영에서 먼저 할 일

```bash
npm run pcu:diag          # 발급한 계정과 응시한 계정을 나란히 적는다
```

**줄을 손으로 만들지 않는다.** `campus_students` 가 없다는 사실만 보고 그
사람에게 줄을 넣으면, 학교가 발급하지 않은 사람이 그 학과의 학생이 된다.
갈린 응시는 그 학생의 것이 아니므로 담당자 집계에서 빼는 것이 맞고, 그
판단은 사업주가 한다.

재배포 뒤에 해야 하는 것은 **발급한 계정으로 다시 밟는 것**이다. 쓰던
브라우저에서 로그아웃하거나 새 창을 열고 `/campus/pcu` 로 들어가
`test001` 로 로그인한다. 그 뒤의 응시는 그 계정의 것이고, 그때 종이와
작업공간과 담당자 집계를 함께 본다.


## P0-2 운영 PDF 는 원인을 확정하지 못했다

**이 세션에서 운영 요청을 추적할 수 없다.** 네트워크 정책이
`app.careermatri.com:443` 을 막고(게이트웨이가 CONNECT 에 403) Railway
Shell 권한도 없다. 그래서 **로컬에서 `200 application/pdf` 가 나온 것을
운영 PASS 로 적지 않는다.** 운영 판정은 `FAIL` 그대로다.

추측으로 fallback 을 만들지 않았다. 대신 **그 자리에서 까닭을 읽을 수
있게** 둘을 했다.

**시작했다는 것을 먼저 적는다.** 전에는 끝났을 때만 적어서, 요청이 이
자리에 닿지 않은 것과 그리는 동안 프로세스가 끊긴 것이 **둘 다 줄 하나
없는 모양**으로 똑같이 생겼다. 이제 `[v3-pdf] start …` 와
`[v3-pdf] done … 바이트 …ms` 가 남는다.

**깨진 까닭은 전부터 운영 표에 적히고 있었다.** 종이가 던지면 그 자리가
걸음(`browser` · `cookie` · `open` · `auth` · `render`)과 까닭을
`job_failures` 에 한 줄 적고, `/admin/incidents` 가 그 글자를 그대로
그린다. 운영자는 Railway 로그 없이도 그 쪽에서 읽을 수 있다.

### 운영에서 읽는 세 걸음

```bash
# 1. 컨테이너 안에서 (Railway → 서비스 → Shell)
npm run pcu:diag          # 읽기만 한다. 아래 여섯을 한 장에 적는다
```

`pcu:diag` 가 적는 것은 이렇다. 환경값(`APP_ENV` · `PLATFORM_URL` ·
`PDF_BASE` · `CHROMIUM_PATH` 와 **그 자리가 실제로 있는가**) · `/me` 와
종이가 읽는 표와 칸 · 그 학생의 줄과 응시와 굳은 결과와 판본 · `/me` 가
고르는 Core · **`job_failures` 의 최근 종이 실패 다섯 줄** · 브라우저가
실제로 뜨는가와 **제 주소로 다시 들어갈 수 있는가.**

뒤의 둘이 운영에서만 나는 실패의 거의 전부다. 그리는 브라우저는 제
주소로 다시 들어가야 하고, 거기서 막히면 종이는 `step=open` 으로
떨어진다.

```bash
# 2. Railway 로그
[v3-pdf]            # start 가 있고 done 이 없으면 그리다 끊긴 것이다
1072622569          # 그 참조 번호의 stack (Next 가 digest 와 함께 적는다)
```

```bash
# 3. 브라우저로 운영자 화면
/admin/incidents    # kind=pdf 줄의 message 가 곧 그 까닭이다
```

**PASS 는 로그가 아니라 받은 파일로 정한다.** 실제로 열리고 `200` 과
`application/pdf` 이고 배재대학교와 경영학과와 경영 영역과 응답일과
설명할 수 있는 경험과 부족한 부분과 다음 할 일이 적혀 있어야 한다.


## P0-3 `/me` 오류 화면의 원인을 찾았다

`career_profiles.recomputed_at` 이 `NOT NULL DEFAULT now()` 다. 그래서
**그 표에 줄을 만드는 자리가 전부 그 칸을 채운다.** 제출이 끝나면
`syncProfile()` 이 고른 산업과 직무와 조직을 지금 값으로 옮기려고 줄을
하나 만드는데, 그 줄의 `gaps` 는 칸 기본값인 `{}` 이고 `recomputed_at` 은
그 순간이다.

읽는 쪽은 반영 여부를 그 시각으로 물었다(`const applied = !!prof?.at`).
그러면 **아무것도 반영하지 않은 사람이 반영한 사람으로** 읽히고, 그
다음 줄이 `{}` 를 배열로 알고 `live.some(...)` 을 부르다 던진다.

```
제출 → syncProfile 이 줄을 만든다(gaps={} · recomputed_at=now())
     → /me 가 그것을 반영으로 읽는다
     → JSON.parse("{}").some(...)  TypeError
     → 오류 화면
```

`currentState()` 는 화면 다섯이 읽는 한 자리라, 한 번 던지면 `/me` 와
`현재 상태` 와 `다음 할 일` 이 함께 넘어간다. 결과지는 그 함수를 읽지
않아서 **결과는 멀쩡히 서고 작업공간만 깨졌다.**

**빈 자리가 하나도 없는 사람에게는 나지 않는다.** `gaps.filter(...)` 가
모델의 빈 자리를 하나도 못 찾으면 콜백을 한 번도 부르지 않는다. 그래서
응답에 따라 나기도 하고 안 나기도 했고, **이 기계의 흐름 검사가 그것을
지나갔다**: 검사가 눌러 주는 응답은 빈 자리를 남기지 않는다.

### 고친 자리

반영 여부를 시각으로 묻지 않는다. 반영된 값을 적는 자리는
`applyRecompute()` 하나이고 그쪽은 `gaps` 를 **배열로** 적는다. 칸
기본값은 객체다. 그래서 `배열인가` 가 곧 `반영된 적이 있는가` 이고,
여기에 짐작이 들어가지 않는다.

```sql
(jsonb_typeof(gaps) = 'array') AS applied,
CASE WHEN jsonb_typeof(gaps) = 'array'
     THEN to_char(recomputed_at, 'YYYY-MM-DD') END AS at
```

시각도 반영된 때만 내놓는다. 아직 반영하지 않은 사람에게 제출 시각을
`최근 반영` 으로 적으면 그 화면이 거짓을 적는다.

**스키마를 바꾸지 않았다.** 뿌리는 `DEFAULT now()` 이고 그것을 고치는
일은 migration 이라 이 회차의 범위 밖이다. 읽는 자리를 고치면 제품이
바로 맞고, 그 칸의 뜻이 왜 못 믿을 값인지는 그 자리에 적어 두었다.

**옛 굳은 결과에 없는 칸을 견딘다.** 결과 모델에 칸을 더한 날 그 전에
응시한 사람의 줄에는 그 칸이 없다. 결과지 쪽은 전에 같은 자리를 겪어
고쳐 두었는데 작업공간의 `openActions()` 만 빠져 있었다.

### 되돌려 보고 걸리는 것까지 확인했다

`npm run v3:recompute` 에 두 줄을 더했다. 제출만 한 사람의 모양을 만들어
보고 되돌린다.

```
통과  제출만 한 사람의 작업공간이 던지지 않는다 — 빈 자리 4개로 돌렸다
통과  제출만 한 것을 반영으로 읽지 않는다 — PRO_DONE · 반영 전
```

고친 자리를 되돌리면 둘 다 걸린다(`live.some is not a function`).
**던지는지만 세면 모자라다**: 빈 자리가 없는 사람에게는 던지지 않아서
그 줄이 아무것도 말하지 않는다. 뒤엣줄은 빈 자리가 없어도 걸린다.


## 담당자 집계는 로컬 PASS 이고 운영은 미확인이다

학생 하나로는 다섯 명 규칙에 걸려 단과대학과 학과와 Core 의 쪼갠 줄이
서지 않는다. **그것은 정상이고 FAIL 이 아니다.** 그래서 재는 것을 둘로
나눈다.

```
통과  전체 응시에 들어간다 — 1
통과  완료에 들어간다 — 1
통과  5명 미만이면 쪼갠 줄을 내지 않는다 — 단과대학 0줄 · 학과 0줄 · Core 0줄
통과  단과대학 줄이 선다 — 1줄
통과  학과 줄이 선다 — 경영학과
통과  Core 줄이 선다 — 1줄
통과  학과 칸의 수가 DB 의 수와 같다 — 화면 6 · DB 6
```

**넣은 수를 세지 않는다.** 그 학과에 앞서 돌린 응시가 남아 있을 수 있어
화면의 수가 넣은 수와 다르다. DB 에 묻고 그 값과 견준다.

운영에서는 담당자 계정으로 `/org/v3` 를 열어 전체 응시와 완료가 실제
DB 와 맞는지만 본다. 그 학생이 PCU 로 묶이려면 기관 줄과 소속이 있어야
하고, `pcu:diag` 의 `기관 소속` 줄이 그것을 적는다.


## 초기 비밀번호를 잃어버렸을 때

재배포로 `/tmp` 가 비면 발급 때 받은 파일이 사라진다. **들고 있던 열쇠를
되살릴 길은 없다**: 해시만 남기는 것이 설계이고, 그것을 되살릴 수 있으면
그 설계가 뜻을 잃는다. 그래서 새로 하나 내고 그 자리에서 한 번 보여 준다.

명단으로도 `ROTATE=yes` 가 돌지만 **그 길은 CSV 에 적힌 이름과 학과를 그
사람의 줄에 다시 쓴다**(`ON CONFLICT DO UPDATE`). 잃어버린 열쇠를 다시
내는 자리에서 바꿀 것은 하나뿐인데, CSV 를 손으로 적다 한 칸이 어긋나면
그 학생의 이름이나 학과가 조용히 갈리고 그 응시는 담당자 화면에서 남의
학과 줄에 선다. 그래서 한 사람짜리 자리를 따로 둔다.

```bash
APPLY=yes ROTATE=yes npm run pcu:students rotate test001
```

**자물쇠가 둘이다.** `APPLY=yes` 만 주면 누구인지 적고 멈춘다. 둘을 함께
주어야 바뀐다. 아이디를 빼면 쓰임을 적고 멈춘다.

**바꾸는 칸이 `password_hash` 하나다.** 아이디와 user id 와 이름과 상태와
학번과 단과대학과 학과와 갈래가 그대로이고, 소속과 응시와 결과와 학과
매핑은 건드리지 않는다. 적어 두는 것으로 두지 않고 **고친 뒤에 그 값을
다시 읽어 센다**: 그 줄이 틀리면 학생의 학과가 조용히 갈리는 자리다.

**그 학교의 발급 계정만 받는다.** `campus_students` 줄이 없는 사람은
거절한다. 담당자 계정의 열쇠는 그쪽 자리가 따로 있다(`pcu:org`).
**아이디로만 찾는다**: 로그인 쪽은 이메일도 받지만, 여기서 이메일로도
찾으면 같은 글자를 든 다른 사람의 열쇠를 바꿀 수 있다.

**새 열쇠는 화면에 한 번만 선다.** 파일을 만들지 않고 DB 에도 로그에도
평문을 두지 않는다. 또 내면 그때 것이 되고 앞의 것은 그 자리에서 죽는다.

## 운영에서 사람이 치고 누를 것

재배포가 먼저다. 고친 것이 전부 이미지 안으로 들어가는 파일이다. DB
스키마는 한 줄도 바뀌지 않았다.

```bash
npm run db:verify     # 핵심 표 7/7 · ME_V3 5/5 · 내 CareerMatri 5/5
npm run ops:check     # DEPLOY 줄에 지금 돌고 있는 SHA 가 적힌다
npm run pcu:diag      # 읽기만. 종이와 작업공간의 자리를 한 장에
```

| | 누를 것 | 정상이라면 | FAIL 기준 |
|---|---|---|---|
| 1 | 결과에서 `결과 PDF 저장` | 파일이 열리고 학교와 학과와 경영 영역이 적힌다 | 안 받아지거나 `PDF를 만들지 못했습니다` |
| 2 | `내 CareerMatri로 돌아가기` | `/me` 가 서고 경영 맥락이 남는다 | 오류 화면 |
| 3 | 담당자 계정으로 `/org/v3` | 전체 응시와 완료에 그 학생이 잡힌다 | 0 으로 선다 |

**셋이 다 PASS 하기 전까지 BIZ 전체 공개와 PCU 전체 공개를 하지 않는다.**
