# 79. 오프라인 하드닝 (보고 A~Q)

> Railway Shell 과 운영 브라우저를 쓸 수 없는 상태에서, **저장소와
> 로컬·테스트 환경만으로 확실히 검증할 수 있는 것**만 했다. 새 제품 기능은
> 만들지 않았다.
>
> **운영 DB · 실제 OAuth 공급자 · `app.careermatri.com` 에는 한 번도
> 접근하지 않았다.** 이 문서의 어떤 줄도 그것을 확인했다고 말하지 않는다.

## A. 이 회차의 기준

묻는 것은 `돈다` 가 아니라 **`사람을 들이기 전에 조용히 틀리는 자리가
남아 있는가`** 다. 그래서 고친 것의 절반이 **검사 자신**이다. 틀린 답을
내던 검사 다섯을 찾았고, 그 다섯이 지금까지 초록이었다.

건드리지 않은 것: 채점 · 문항 은행 · ResultModel 의 판단 · 등급 구조 ·
산업과 역할이 Core 를 바꾸지 않는 원칙 · 굳은 스냅샷 · 상품 활성화 ·
PG 운영 연결 · `publicCommerceGate`.

## B. 개발용 열쇠를 저장소에서 없앴다

| | |
|---|---|
| 소스에서 지운 평문 | 24자리 (스크립트 10벌) |
| 문서에서 지운 평문 | 6자리 (`README.md` · `48_qa_local.md`) |
| 받는 자리 | `scripts/dev-credentials.mjs` 하나 |

**값을 바꾸지 않고 없앴다.** 개발용이라도 그 값으로 **실제로 로그인이
된다**: 개발 DB 가 잠깐 열린 날 저장소를 읽은 사람이 그대로 들어온다.

- 환경변수(`DEV_SEED_PW_<역할>`) → `.dev-credentials.json`(gitignore,
  mode 600) → **그 자리에서 만든다**(`randomBytes(18)`)
- **운영에서는 아예 멈춘다**: `APP_ENV=production` 이면 `devPassword()` 가
  던진다
- 역할마다 다른 값이다. 공통값을 쓰면 한 자리가 새면 전부 샌다
- 시드가 끝나고 적는 안내는 **값을 찍지 않는다.** 어디를 보라고만 적는다

`npm run secrets:check` 가 일곱 가지를 센다. 지웠던 값 7개가 글자로
돌아왔는지 · 비밀번호 자리에 평문이 박혔는지 · 운영 열쇠 모양이 적혔는지 ·
열쇠 파일이 git 에 들어왔는지 · 쓰는 스크립트가 한 자리에서 받는지 ·
운영에서 멈추는지.

**코드에서는 주석을 걷어 내고 센다.** 이 저장소는 `왜 지웠는가` 를 주석으로
남기는 쪽을 택했고 그 기록에는 지운 값이 그대로 들어 있다. 그것까지 세면
**맞는 기록을 지우라고 요구하게 된다**(`launch:check` 가 옛 법인 표시를 셀
때 같은 판단을 했다). 문서(`.md`)는 걷어 내지 않는다: 거기는 전부가 사람이
읽는 글이고, 값이 적혀 있으면 읽은 사람이 그대로 쓴다.

## C. 예외 삼키기 전수 분류

`catch` 153자리를 전부 보고 세 갈래로 적었다. **모든 catch 를 throw 로
바꾸지 않았다**: 그러면 메일 서버가 느린 날 결제가 같이 멈춘다.

| 갈래 | 자리 | 뜻 |
|---|---|---|
| MUST FAIL | 9구역 | 돈 · 신원 · 동의 · 채점 · 굳은 결과. 삼키면 안 된다 |
| NEEDS LOGGING | 6자리 | 기능은 계속되지만 운영 로그가 있어야 한다 |
| SAFE | 5자리 + 나머지 | 삼키는 것이 **설계**인 자리 |

고친 것 넷이다.

- **`consent.record()` 가 실패해도 `{ok:true}` 를 돌려줬다.** INSERT 가
  거절돼도 화면은 가입을 끝냈고, 그러면 **동의 기록 없는 계정**이 남는다.
  분쟁에서 댈 것이 없는 자리다. 필수 문서는 이제 실패를 돌려준다
- **`pilot.saveFeedback()` 이 실패한 쓰기를 센 수에 넣었다.** `.catch(() =>
  null); n++` 였다. 파일럿은 한 번뿐이라 잃은 줄을 다시 못 받는다
- 가입 되돌리기 두 자리(`signup` · `signup/social`)의 `DELETE` 가 조용했다.
  **되돌리기가 실패하면 그것이 더 큰 일이다**: 동의 없는 계정이 남는다
- **`portone.refund` 가 응답을 못 읽은 것을 버렸다.** 돌려주는 말에 담기는
  것은 상태 코드뿐이라 **PG 가 거절한 것과 본문이 깨진 것이 밖에서 같은
  상태로 보였다.** 환불 번호가 `null` 로 적히는 쪽도 같다

`npm run errors:check` 가 여덟 가지를 센다. 가장 중요한 설계는 **`까닭 없이
비운 catch` 만 센다**는 것이다. 까닭을 적어 둔 catch 까지 세면 고치는 쪽이
**까닭을 지우고 `console.error` 를 적어** 통과시킨다. 그 거래는 손해다.
그래서 SAFE 자리는 목록에 까닭과 함께 적고, **그 까닭이 지워지면 걸린다.**

## D. 오류 한 줄이 다섯을 적는다

`src/lib/oplog.ts` 하나다. 운영에서 `pdf failed` 를 본 사람이 로그를
뒤져도 아무 줄이 없었던 자리의 뒤처리다.

```
[op] consent.record ref=user#182 step=insert cat=db at=2026-10-09T… detail=… :: <한 줄>
```

- `operation` · `ref` · `step` · `category` · `at` 다섯이 늘 선다
- **개인정보를 적지 않는다.** `ref()` 가 들어온 값을 검사해서 `@` 가 있거나
  너무 길면 길이만 적는다. **적는 사람이 실수해도 로그에는 안 들어간다**
- `why()` 가 한 줄만 꺼낸다. stack 은 적지 않는다
- **사용자 화면에 이 줄을 내보내지 않는다.** 화면에는 무엇을 할 수 있는지를
  적고, 이 줄은 고치는 사람이 읽는다. `errors:check` 가 `src/app` 에서
  `{e.stack}` 모양을 센다

## E. 신규 사용자가 옛 엔진에 들어갈 길

**edge 0 이다.** 글자로 적어 둔 옛 검사 주소가 `engine-entry.ts` 한 곳뿐이고,
신규 진입면과 공용 띠에서 `/test` · `/assessment/start` 로 가는 줄이 없다.

고친 자리 넷이 나왔고 **하나는 진짜였다.**

- **`/checkout/complete` 가 새로 산 사람을 `/test` 로 보냈다.**
  `startPathFor()` 가 `null` 인 분기(산 상품이 옛 판본)에서 판본을 보지 않고
  **늘 ME_V1** 을 열었다. ME_V2 를 산 사람이 120문항 앞에 앉는다. 위에 적어
  둔 주석은 `지원으로 보낸다` 였는데 **코드가 그렇게 하지 않았다**
- `/pricing` · `/my` 의 ME_V2 이어하기와 `/my/assessments` 의 ME_V1
  이어하기는 보존이 맞는 자리라 지우지 않고 `resumePathFor()` 로 옮겼다

**제 구역 안을 가리키는 것은 세지 않는다.** 옛 검사 안의 쪽이 제 시작
화면으로 돌려보내는 것은 그 판본으로 응시하던 분을 제자리로 보내는 줄이고,
그것까지 세면 보존하기로 한 길이 스스로 끊긴다.

## F. route 소유 표

`ROUTE_TABLE` 44줄이고 `npm run routes:check` 가 실제 `src/app` 과 대조한다.

```
CURRENT 25 · COMPATIBILITY 14 · REDIRECT 4 · DEPRECATED 1
미분류 0 · 중복 0 · 없는 쪽 0 · 소유 구역 밖 47쪽
```

**`src/app` 전체를 표에 적지 않는다.** 운영 화면과 기관 화면은 어느 검사로
들어가는가와 상관이 없고, 그것까지 적으면 표가 쪽 목록이 되어 아무도 안
고친다. 세는 구역은 `OWNED_SEGMENTS` 에 적어 두었고 **그 구역에 쪽을 하나
더하면 표를 고치기 전까지 걸린다**(일부러 하나 더해 확인했다).

## G. Google 로그인: 코드 쪽 준비

`npm run oauth:ready` 열한 가지. **구글에 붙지 않는다**: 붙으려면 자격증명이
있어야 하고, 있어도 사람이 브라우저에서 동의를 눌러야 한다.

- 요구 범위가 `openid email profile` 뿐이다. 드라이브·달력·연락처를 요구하지
  않는 것을 검사가 센다. **안 받은 것은 샐 수 없다**
- 값이 없으면 공급자가 **등록조차 되지 않는다**(실제로 환경변수를 빼고 불러
  확인했다). 등록해 두면 `/api/auth/signin/google` 이 열려 있고 누른 사람이
  `invalid_client` 를 받는다
- **반만 꽂히면 켜지지 않는다.** 꽂은 사람은 켜졌다고 생각하므로 그 상태를
  `ops:check` 의 `OAUTH` 줄이 적어 준다
- 신원을 찾는 열쇠가 `sub` 이다. 이메일로 찾으면 구글에서 주소를 바꾼 사람이
  다음 로그인에 새 계정으로 떨어진다

## H. Apple 로그인, 그리고 **만료되는 열쇠**

구글의 secret 은 지우지 않으면 계속 산다. 애플은 우리가 만들어 넣는 JWT 이고
**애플이 받아 주는 최대 수명이 180일**이다. 그래서 아무것도 고치지 않아도
어느 날 애플 로그인만 멈추고, 멈춘 쪽은 애플 단추를 누른 사람뿐이라 운영
화면에서 눈에 띄지 않는다.

갱신 절차를 `docs/metri/77_oauth_ops.md` 에 적었다. **값과 열쇠는 문서에
적지 않았고**, 검사가 그 문서에 `-----BEGIN … PRIVATE KEY-----` 나 값이 든
`AUTH_APPLE_SECRET=` 이 들어오는 것을 막는다. 추적되는 파일에 `.p8` 가 있으면
걸린다.

**자동 갱신을 만들지 않았다.** 만들려면 `.p8` 개인키를 앱이 읽을 수 있는
자리에 둬야 하고, 그러면 그 키가 앱이 깨진 날 같이 샌다. 애플 로그인 하나를
편하게 하려고 Sign in with Apple 의 뿌리 열쇠를 서버에 두는 거래는 손해다.
대신 **잠기지 않게** 해 두었다(아래 I).

## I. 계정에서 잠기지 않는가 (여덟 가지)

`auth:check` 가 37가지를 세고 그중 15절이 이 여덟이다. 앞의 열넷은 **같은
사람이 둘로 갈리지 않는가**였고, 그 쪽으로만 조이면 **공급자가 막힌 날 남는
길이 없다.**

| | 묻는 것 | 결과 |
|---|---|---|
| ① | 소셜만 든 계정은 비밀번호 로그인이 꺼져 있다 | 통과 |
| ② | 비밀번호를 정하면 `pw_login` 이 같이 올라간다 | **고쳤다** |
| ③ | 마지막 로그인 방법을 끊는 길이 손님 쪽에 없다 | 통과 |
| ④ | 공급자 쪽 메일이 바뀌어도 같은 계정이다 | 통과 |
| ⑤ | 애플의 가려 준 주소를 끈 뒤에도 같은 계정이다 | 통과 |
| ⑥ | 멈춘 자리가 복구 경로 셋을 가리킨다 | 통과 |
| ⑦ | 공급자를 꺼도 비밀번호 로그인이 남는다 | 통과 |
| ⑧ | 파기·정지된 계정은 소셜로도 못 들어온다 | 통과 |

②가 진짜였다. **비밀번호 재설정과 변경이 해시만 바꾸고 `pw_login` 을
`false` 로 남겨 뒀다.** 소셜로 만든 계정은 그 칸이 `false` 인데, 비밀번호를
정하면 그 순간부터 비밀번호로 들어올 수 있다. 칸을 그대로 두면 `/my` 의
`로그인 방법` 이 **들고 있는 열쇠를 없다고 적고**, 공급자 쪽이 막힌 날 그
사람은 자기가 잠긴 줄 안다.

⑦은 글자로만 재지 않는다. `Credentials` 가 `providers` 배열에 **조건 없이**
서 있는지를 본다. 앞에 `if` 나 삼항이 붙으면 공급자 값을 잘못 빼는 날 같이
빠진다.

## J. 파일럿 판본 기록: 값까지

`npm run pilot:ready` 가 실제 DB 로 한 사람을 끝까지 풀리고 그 줄을 읽는다.

```
판본 12칸. 비어 있으면 안 되는 9칸이 차 있고, 코드의 상수와 글자까지 같다
비어 있는 것이 맞는 3칸: 산업팩 · 역할팩 · 지역 층 (까닭을 함께 적는다)
```

**이것을 따로 둔 까닭.** `v3:owner` 가 이미 `칸이 열둘 있다` 를 세는데 그것은
`k in obj` 다. **칸이 있고 값이 `null` 이면 통과한다.** 끝난 뒤에 묻는 것은
칸의 수가 아니라 **그 사람이 어느 판본을 읽었는가**이고, 값이 비면 그 물음에
답할 수 없다. 상수만 올리고 적는 자리를 안 고치면 올린 다음 응시가 **옛
판본으로 적힌다**(일부러 그렇게 만들어 걸리는 것을 확인했다).

## K. 파일럿 analytics: 중복과 누락

세 목록이 `analytics_events` 를 같이 쓰는데 묻는 것이 다르다.

| 목록 | 묻는 것 | 걸음 |
|---|---|---|
| 상용 퍼널 | 방문이 결제가 되는가 | 9 |
| 작업공간 | 결과를 받은 사람이 다시 들어오는가 | 8 |
| 파일럿 | 어디서 멈췄는가 | 13 (`v3_pilot.` 꼬리표) |

- **이름 겹침 0.** 한 이름이 둘에 있으면 어느 쪽 수도 못 믿는다
- **적는 자리 없는 걸음 0.** 목록에 이름만 적어 두면 운영 표에 늘 0 으로
  서고, 읽는 사람은 `아무도 거기까지 안 갔다` 고 읽는다
- **중복을 글자로 보지 않고 실제로 두 번 불러 봤다.** 파일럿 쪽은 한 줄만
  적힌다(사람으로 세는 것이라). 작업공간 쪽은 **일부러 매번 적고** 읽을 때
  `count(DISTINCT user_id)` 로 센다. 둘의 비가 곧 다시 들어온 횟수다
- 시연 자료가 작업공간 지표에 섞이지 않는다(`du.is_demo`)

## L. 운영 파일럿 화면

**판본을 줄에만 적어 두고 화면이 보여 주지 않았다.** 그러면 파일럿 중에
판본이 올라간 것을 아무도 모르고, 앞사람과 뒷사람의 결과를 한 묶음으로
분석한다. 끝난 뒤에는 되돌릴 수 없다.

- 한 사람 화면(`/admin/v3-pilot/<id>`)에 `이 응시가 읽은 판본` 표를 세웠다.
  **결과에 닿는 셋을 앞에 두고 그 사실을 적는다.** 비어 있는 칸은
  `고르지 않음` 으로 적고 숨기지 않는다
- 표 쪽(`/admin/v3-pilot`)은 **wave 안에서 판본이 섞였는지**를 맨 위에
  적는다. 결과에 닿는 판본이 갈린 것과 화면·문장이 갈린 것을 나눠 적는다:
  앞엣것은 분석을 나눠야 하고 뒷엣것은 읽을 때 알아야 하는 일이다
- 전공명은 두 화면 어디에도 나가지 않는다(준식별자다)

## M. 백업·복구: 로컬 예행

로컬 PostgreSQL 로 한 바퀴 돌렸다. **운영 DB 에는 한 줄도 쓰지 않았고 받은
적도 없다.**

```
표 14개의 줄 수가 같다 · 제약 열 가지 · 외래키 216개
결과지 29장이 열린다 · 지금 판본 결과지 7장이 판본과 함께 돌아왔다
```

**세는 아홉 표가 전부 ME_V1·V2 때의 것이었다.** 지금 파는 판본의 응시와
결과와 지금 상태(`v3_attempts` · `v3_responses` · `v3_snapshots` ·

`줄 수가 같다` 를 찍고 지나갔다. 돈을 낸 사람의 결과지는 지금
`v3_snapshots` 에 있다.

- 표 목록을 **한 자리에 두었다**. 두 곳에 적어 두면 표를 더하는 날 한쪽만
  늘고, 그것이 마이그레이션 목록이 두 벌이었던 장애의 모양이다

## Q. 이 기계에서 확인하지 못한 것

**아래는 통과도 실패도 아니다. 보지 못한 것이다.**

| 묻는 것 | 왜 못 봤는가 |
|---|---|
| 운영 DB 가 지금 코드까지 올라와 있는가 | Railway Shell 권한이 없다 |
| 운영 볼륨에 PDF 가 남는가 | 같은 까닭 |
| 실제 PG 로 결제가 되는가 | 사람이 카드로 해야 한다 |
| 실제 구글·애플 로그인이 되는가 | 자격증명이 없고, 있어도 사람이 눌러야 한다 |
| 공급자 콘솔에 돌아올 주소가 등록됐는가 | 콘솔 쪽 상태다. 코드가 알 수 없다 |
| `app.careermatri.com` 이 지금 서 있는가 | 네트워크 정책이 그 호스트를 막는다 |
| 운영 백업을 되돌릴 수 있는가 | 운영 DB 를 받지 않았다. **로컬에서만 돌렸다** |
| `auth_accounts` 표가 운영에 섰는가 | `db:verify` 가 컨테이너에서 답한다 |

두 가지를 적어 둔다. 첫째, 이 컨테이너에는 지난 회차가 남긴
`/app/server.js` 가 있어서 `ops:check` 의 `inDeployment()` 가 **이 기계를
배포본으로 읽는다.** 그래서 이 기계의 `ops:check` 출력은 운영 상태가 아니다.
탐지기를 약하게 고치지 않았다: 실제 배포본에서는 그 판단이 맞다. 둘째,
사보타주 시험 중에 로컬 QA DB 의 파일럿 예행 스냅샷 한 줄(`is_demo` 계정)의
굳은 결과를 비웠고, **원래 값을 저장하지 못해** 같은 payload 와 지금 엔진으로
다시 만들어 넣었다. 로컬 개발 DB 의 예행 자료이고 지금은 빈 줄이 0 이다.
