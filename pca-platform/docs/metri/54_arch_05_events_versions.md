# K. 자동화 event 구조 · L. version 구조

## 1. 검사가 끝나도 끝나지 않는다

```
결과 저장 → 새 경험 추가 → Evidence 업데이트
→ 산업·역할·지역 변경 시 재분석 → Gap 재계산 → 다음 행동 업데이트
```

이 고리가 돌려면 **다시 계산해야 할 일**을 담는 자리가 필요하다.

## 2. 표가 셋이 되는 것이 맞는가

이미 둘이 있다. 셋째를 만들기 전에 각자가 묻는 질문을 적는다.

| 표 | 묻는 질문 | 담지 않는 것 |
|---|---|---|
| `analytics_events` | 방문이 결제가 되는 비율은 얼마인가 | 자유입력 · 결과지 본문 · 재계산 거리 |
| `outbox` | 이 메일이 나갔는가 | 열쇠 · 결과지 본문 |
| `career_events` | 무엇을 다시 계산해야 하는가 | 자유입력 · 결과지 본문 |

셋이 묻는 것이 다르다. 퍼널에 재계산을 섞으면 **전환율이 거짓**이 되고,
메일 대기열에 섞으면 **메일이 안 나가는 날 재계산이 멈춘다.**

## 3. `career_events`

| 칸 | 뜻 |
|---|---|
| `kind` | 열 가지. 아래 표 |
| `payload` | 다시 계산하는 데 필요한 최소값 |
| `dedupe_key` | 같은 일로 두 번 돌지 않게 **DB 가 막는다** |
| `status` | `queued` · `running` · `done` · `failed` · `skipped` |
| `attempts_n` · `last_error` | 몇 번 해 봤고 왜 멈췄는가 |

| 종류 | 언제 | 무엇을 돌린다 |
|---|---|---|
| `attempt.scored` | 채점이 끝났다 | 결과 생성과 스냅샷 |
| `evidence.added` | 경험이 늘었다 | 축 수준 재계산 · Gap |
| `evidence.edited` | 경험이 바뀌었다 | 같다 |
| `target.changed` | 목표 산업이나 역할이 바뀌었다 | 산업·역할 해석 재적용 |
| `region.changed` | 희망 지역이나 이동 범위가 바뀌었다 | 지역 절만 |
| `pack.updated` | 산업팩이나 역할팩 판본이 올라갔다 | 그 팩을 쓴 사람의 해석 |
| `posting.ingested` | 공고 자료가 들어왔다 | Gap 대조 (3단계) |
| `gap.recomputed` | Gap 을 다시 계산했다 | 다음 행동 갱신 |
| `report.refreshed` | 결과를 다시 냈다 | 알림 |
| `digest.due` | 월간 리포트 때가 됐다 | 리포트 생성 (4단계) |

**멱등이 DB 에 있다.** `dedupe_key` 에 유일 인덱스를 걸어서, 웹훅과 화면이
같은 순간에 들어와도 두 번째가 그 자리에서 거절된다. 읽고 판단한 뒤 쓰면
둘 다 통과한다(무료 주문 번호와 같은 설계다).

## 4. 지금 값과 굳은 값을 가른다

| 표 | 무엇 | 바뀌는가 |
|---|---|---|
| `report_snapshots` | 그때 낸 결과지 | **바뀌지 않는다.** 줄이 쌓이기만 한다 |
| `career_profiles` | 지금의 축 수준과 묶음과 Gap 과 목표 | 바뀐다 |

한 표에 담으면 갱신이 스냅샷을 덮어서 **만들어 둔 결과지를 고치지 않는다**
가 깨진다. 산 사람이 열어 본 결과지가 어느 날 달라지면 그 제품은 못 판다.

## 5. 자동화 네 단계

전부를 한 번에 만들지 않는다. **앞 단계가 돌아야 다음이 의미가 있다.**

| 단계 | 무엇 | 지금 |
|---|---|---|
| 1 | 검사 내부 자동화 (routing · 선별 · 심화 개방 · 결과 생성) | 설계 끝 · 구현 전 |
| 2 | 검사 이후 자동화 (Evidence 추가 · Gap 재계산 · 결과 갱신) | 스키마만 |
| 3 | 외부 자료 (공고 수집 · taxonomy 사상 · Gap 대조) | **저작권 검토 전** |
| 4 | 구독 (월간 리포트 · 메일 · 반복결제) | 표 종류만 |

3단계가 2단계보다 뒤인 까닭은, **공고를 모으기 전에 내 Gap 이 먼저 서
있어야** 비교가 뜻을 가지기 때문이다.

## 6. 구독은 산업팩을 잠그지 않는다

산업팩과 역할팩은 진단에 포함된다. 구독이 붙는 자리는 **계속 갱신되는
기능**이다.

| 구독이 파는 것 | 왜 구독인가 |
|---|---|
| 관심 산업 공고 자동 추적 | 자료가 계속 바뀐다 |
| 산업별 요구역량 변화 | 같다 |
| 내 Evidence 와 공고 대조 | 둘 다 바뀐다 |
| Gap 자동 갱신 | 경험이 늘면 다시 센다 |
| 월간 Career Report | 매달 새로 만든다 |
| 목표 바뀔 때 재분석 | 사람이 바꾼다 |
| 지원 직무 관리와 알림 | 계속 돈다 |

표는 새로 만들지 않고 `entitlements.kind` 에 `track` 을 더한다.
**산업팩을 잠그는 종류를 만들지 않는다.**

## 7. L. version 구조

모듈마다 판본을 따로 올린다.

```
ME_CORE_V3            전공 Core
INDUSTRY_SEMICON_V1   산업팩
ROLE_CAE_V1           역할팩
REGION_KR_V1          지역 layer
```

| 어디에 | 무엇 |
|---|---|
| `major-cores.json` 의 `code` | Core 판본이 코드 안에 있다 |
| 팩 파일의 `version` | 팩마다 정수 하나 |
| `report_snapshots.module_versions` | **그때 실제로 돌아간 모듈과 판본** |
| `attempts.assessment_version` | 어느 검사지로 풀었는가 |

`module_versions` 를 칸 하나(JSONB)로 둔 까닭은 모듈이 계속 늘기 때문이다.
모듈마다 칸을 만들면 팩을 더할 때 스키마를 바꾸게 된다.

```json
{"core": "ME_CORE_V3",
 "industry": "INDUSTRY_SEMICON_V1@1",
 "role": "ROLE_CAE_V1@1",
 "region": "REGION_KR_V1@1"}
```

### 7-1. 판본을 손으로 적지 않는다

지금 `report_snapshots` 의 엔진 판본 다섯은 **실제로 돌아간 파일의 지문**
이다. 파일 안에 판본을 적어 두면 고치면서 올리는 것을 잊고, 잊으면 스냅샷이
거짓을 적는다. `module_versions` 도 돌린 자리가 적는다.

### 7-2. 하나만 올릴 수 있다

| 올리는 것 | 영향 |
|---|---|
| 산업팩 하나 | 그 팩을 쓴 응시의 **해석**만. 축 수준은 그대로 |
| 역할팩 하나 | 같다 |
| 지역 layer | 지역 절만 |
| Core | **새 판본이다.** 옛 판본은 읽기 전용으로 잠근다 |

Core 를 올리는 것만 판본 교체이고 나머지는 모듈 갱신이다. 그 차이를
`pack.updated` 와 새 `assessment_version` 이 가른다.
