# Wave 1 Core Authoring 착수 분석 (2026-10-12)

**이 문서는 분석이고 구현이 아니다.** 문항을 한 줄도 쓰지 않았고 Core 파일을
하나도 만들지 않았다. 적는 것은 무엇을 어떤 차례로 만들 것인가와, 그것이
지금 엔진에 어떻게 붙는가다.

구조는 그대로다.

```
Market → Major Core → Industry Pack → Role Pack → Region Layer
       → Evidence/Gap → Career Action
```

**한국과 글로벌에 채점 엔진을 따로 만들지 않는다.** 같은 Core 를 두 시장이
함께 쓰고, 갈리는 것은 `markets` 와 Industry·Role·Region 층뿐이다.

---

## 1. 먼저 만들 Core 와 그 Core 가 여는 자리

차례가 곧 만드는 차례다. **학과 이름 대신 Core 로 적는다**: 두 해의
이름이 달라도 같은 Core 를 다시 쓰기 때문이다.

| 차례 | Core | 2026 자리 | 2027 자리 | 자리 수 |
|---|---|---|---|---|
| 1 | `EE_CORE_V1` 전기전자공학 | 전기전자공학과 | 전기공학과 · AI융합전자전공 | 3 |
| 2 | `CS_CORE_V1` 컴퓨터·소프트웨어 | 소프트웨어공학부 4전공 | AI소프트웨어공학부 5전공 | 9 |
| 3 | `BIZ_CORE_V1` 경영학 | 경영학과 · IT경영정보학과 · 글로벌비즈니스학과 | 같음 | 6 |
| 4 | `PUBADM_CORE_V1` 행정학 | 일반행정트랙 · 소방행정트랙 | 같음 | 4 |
| 5 | `BT_CORE_V1` 바이오·생명공학 | 생명공학과 | 생명공학과 | 2 |

다섯을 다 만들면 두 Catalog 에서 **스물넷**이 열린다. 지금 열려 있는 자리는
0이다.

**전부를 한꺼번에 만들지 않는다.** 하나를 끝까지 만들어 검사와 결과지가
실제로 도는 것을 보고 다음으로 간다. 다섯을 나란히 열면 어느 Core 에서
구조가 틀어졌는지 가려낼 수 없다.

## 2. 기존 Core 재사용 가능 여부

| 쓰는 것 | 어디까지 | 새로 만드는가 |
|---|---|---|
| 채점 엔진 (`scoring/*`) | 그대로 | 아니다 |
| 결과 모델 (`result/model.ts` · `build.ts`) | 그대로 | 아니다 |
| 응시 화면 (`/v3/*`) | 그대로 | 아니다 |
| 작업공간 · 결과지 화면 | 그대로 | 아니다 |
| 소유 네 단계와 축 여덟 | 그대로 | 아니다 |
| Industry·Role 팩의 **틀** | 그대로 | 내용은 Core 마다 새로 |
| Region 층 | 그대로 | 아니다 |

**엔진을 뜯지 않고 Core 를 더할 수 있다는 것은 이미 돌려서 확인했다**
(`npm run v3:extend`). 전기전자와 경영 Core 를 임시 자리에 자료로만 만들고
`v3:build` 와 `v3:domains` 와 `v3:items` 를 **한 글자도 고치지 않고** 돌려
열네 가지가 전부 통과했다. 그때 고친 코드는 0줄이다.

그래서 Wave 1 은 **코드 작업이 아니라 자료 작업**이다.

---

## 3. 신규 Core 개발 필요 여부

다섯 Core 는 등록부에 **이름과 별칭과 갈래만** 있다(`status: planned` ·
`maturity: FOUNDATION` · `files: {}`). 자를 새로 만드는 일이 아니고 그
전공의 자료를 채우는 일이다.

| Core | 지금 | 갈래 |
|---|---|---|
| `EE_CORE_V1` | 뼈대만 | 전기·전력 · 전자·회로 · 정보통신 (셋 다 미작성) |
| `CS_CORE_V1` | 뼈대만 | 컴퓨터공학 · 소프트웨어학 · 정보보안 · 게임공학 · 인공지능·데이터 (다섯 다 미작성) |
| `BIZ_CORE_V1` | 뼈대만 | 마케팅 · 생산·운영 · 조직·인사 (셋 다 미작성) |
| `PUBADM_CORE_V1` | 뼈대만 | 없음 |
| `BT_CORE_V1` | 뼈대만 | 없음 |

**갈래는 Core 위에 조정만 얹는 층이다.** 조정하는 것은 다섯(영역 강조 ·
산업 사상 · 역할 사상 · 예시 · 증거와 행동)이고 채점과 축 수준과 묶음
규칙과 문항 은행과 결과 모델은 건드리지 않는다. 갈래를 켜는 일은 그 다섯
층을 적는 일이고 코드를 고치는 일이 아니다.

## 4. 학과별 전공지식·역량·경험 자료의 구성

Core 하나가 서려면 **필수 네 파일**이 있어야 한다(`required_files`).
기계공학이 실제로 쓴 분량이 기준선이다.

| 파일 | 무엇을 담는가 | 기계공학 분량 |
|---|---|---|
| `taxonomy` | 기술영역과 축, 척도와 수준 | 영역 12 · 축 8 |
| `domains` | 영역마다 하는 일의 흐름과 산출물과 검증 대상 | 영역 12 |
| `checklists` | 축마다 고를 수 있는 판단 문장 | 256 |
| `items_blueprint` | 문항 자리와 어느 결과 절로 가는가 | 자리 101 · 결과 절 10 |

그 위에 붙는 것.

| 파일 | 무엇을 담는가 | 기계공학 분량 |
|---|---|---|
| `items` | 문항 문면과 보기 넷 | 369 |
| `relations` | 영역과 산업 · 영역과 역할의 관계 | 96 · 96 |
| `constructs` | 문항마다 무엇을 재는가 | 문항 수만큼 |
| 산업팩 · 역할팩 | 그 전공이 가는 산업과 역할 | 8 · 8 |

**전공을 늘리는 속도는 그 전공을 아는 사람이 쓸 수 있는 속도다.** 기계공학은
영역 사전과 체크리스트를 먼저 끝내고 문항을 썼고, 그 차례를 지키지 않으면
문항과 결과지가 서로 다른 축 위에 선다.

Core 하나의 작업 차례는 넷이다.

1. **영역 사전**: 그 전공의 기술영역과 축 여덟의 뜻을 적는다
2. **체크리스트**: 축마다 고를 수 있는 판단 문장을 적는다. 축 하나에 항목이
   하나뿐이면 소유가 구조적으로 설 수 없으므로 둘 이상을 적는다
3. **문항 자리와 문면**: 받고 쓰지 않는 자리를 0으로 둔다
4. **산업·역할팩과 관계표**: 조합마다 복제하지 않고 더하기로 늘린다

## 5. 기존 채점 엔진에 붙이는 방법

**코드를 고치지 않는다.** 붙는 자리는 등록부 한 줄과 파일 넷이다.

```
major-cores.json 의 그 Core 에
  files: { taxonomy · domains · checklists · items_blueprint }
  status: planned → building
  maturity: FOUNDATION → READY_FOR_REVIEW
```

`status` 가 `building` 이 되는 순간 그 Core 를 가리키는 학과의 학생 표시가
**`준비 중` 에서 `검사 가능` 으로 저절로 바뀐다.** 등록부에 상태를 적어 두지
않고 끌어오기 때문이다. 그래서 **문항이 써지기 전에 상태를 올리면 안 된다**:
올리는 순간 그 학과 학생이 빈 검사를 만난다.

검사는 이미 서 있다.

| 명령 | 무엇을 센다 |
|---|---|
| `v3:domains` | 영역 사전과 체크리스트가 성립하는가 |
| `v3:items` | 문항 자리와 응답 수 |
| `v3:wording` | 문면이 영역 이름만 바꾼 복붙인가 |
| `v3:migrate` | 받고 쓰지 않는 문항 0 · 입력이 없는 결과 절 0 |
| `v3:extend` | 엔진을 뜯지 않고 Core 를 더할 수 있는가 |
| `campus:check` | 그 Core 를 가리키는 학과의 상태가 맞게 바뀌는가 |

`CORE=EE_CORE_V1 npm run v3:domains` 처럼 Core 를 넘겨 돌린다. **검사가
Core 이름을 모르게 짜여 있다**(금지 낱말 검사가 그것을 센다).

## 6. 결과지의 Evidence · Gap · Action 구성

결과 모델은 **공통 한 벌**이고 Core 마다 다시 만들지 않는다. Core 가 채우는
것은 그 모델이 읽는 자료다.

| 자리 | 무엇이 채우는가 |
|---|---|
| Evidence (설명할 수 있는 경험) | 그 사람이 고른 체크리스트 항목과 보기 넷의 자리 |
| Gap (부족한 부분) | 축 여덟 가운데 확인되지 않은 자리 + 그 영역의 필수 축 |
| Action (다음 할 일) | 그 영역의 `verify_targets` 와 `artifacts` 에서 가져온다 |
| 산업·직무 연결 | 관계표(`relations`)의 `중심` 과 `있음` |
| 지역 | Region 층. **기관 자료는 0줄이라 유형까지만 적는다** |

**막연한 말을 쓰지 않는다.** 할 일의 재료를 그 영역의 자료에서 가져오는
것이 그 까닭이고, `역량을 강화하세요` 류를 `v3:result:copy` 가 센다.

**결과지 화면과 PDF 는 손대지 않는다.** 아홉 절과 쪽수 규격이 그대로이고,
Core 가 바뀌어도 읽는 차례는 같다.

## 7. 착수 조건

| 조건 | 지금 |
|---|---|
| `campus:check` 통과 | 76가지 통과 |
| 지난 코드 호환성 | 내린 코드 23개가 다시 서지 않는다. 실제 DB 로 확인 |
| Catalog 정확성 | 2차 근거로 맞췄다. **원본 직접 확인은 미해결** |
| 운영 배포 | **확인하지 못했다** |

**원본 직접 확인이 끝나기 전에 Core 를 쓰기 시작해도 되는가.** 된다.
Core 는 전공의 자이고 학교 편제와 따로 산다. 편제가 뒤집혀도 바뀌는 것은
**어느 학과가 어느 Core 를 가리키는가**이지 Core 자체가 아니다. 다만
`EE_CORE_V1` 과 `CS_CORE_V1` 이 가리키는 자리가 두 해 사이에서 바뀌었던
만큼, **Core 를 여는 날 그 학과 목록을 한 번 더 본다.**

## 8. 하지 않을 것

- 전체 학과에 문항을 한꺼번에 만들지 않는다
- 한국과 글로벌에 채점 엔진을 따로 만들지 않는다
- 이름이 비슷하다는 까닭만으로 Core 를 붙이지 않는다. 스마트배터리학과는
  후보가 셋이라 여전히 비어 있다
- 문항이 써지기 전에 `status` 를 올리지 않는다
