# ME_V2 화면 배선과 경험 연결

규격 ME-V4.0 이 준 92문항을 실제로 응시해 결과를 받는 데까지 이었다.
문항 은행과 채점은 `29_me_v2_assessment.md` 에 있고, 여기는 **사람이 어느
화면을 어떤 순서로 보는가**를 적는다.

```
상품 → 학위 단계 → 섹션별 응시 → 채점 → 경험 입력 → 결과 → 인쇄·PDF
```

## 1. 옛 검사를 건드리지 않는 방법

`app.js` 안에 분기를 넣지 않고 **페이지를 하나 더 두었다**. `index.html` 과
`v2.html` 은 같은 CSS 를 쓰지만 불러오는 스크립트가 다르고, 저장 키도
전역 이름도 겹치지 않는다.

| | ME_V1 | ME_V2 |
|---|---|---|
| 주소 | `index.html` | `v2.html` |
| 화면 코드 | `assets/app.js` | `assets/v2-app.js` |
| 결과지 | `assets/report.js` | `assets/v2-report.js` |
| 결과 JSON | `assets/result-json.js` | `assets/v2-result-json.js` |
| 저장 키 | `pca_session_v1` | `pca_v2_session_v1` |

경험만 같이 쓴다(`pca_evidence_v1` · `pca_research_v1` · `pca_target_v1`).
검사가 둘이어도 사람은 하나고, 캡스톤을 두 번 적게 할 이유가 없다.

`npm run v2:flow` 가 V2 를 다섯 번 풀고 나서 **V1 도 한 번 끝까지 풀어**
점수가 그대로 나오는지 보고, V2 를 푼 뒤에 `pca_session_v1` 이 비어 있는지와
V1 을 푼 뒤에 `pca_v2_session_v1` 이 생기지 않는지도 같이 본다.

## 2. 92문항을 어떻게 나눠 내는가

한 문항씩 넘기면 92번을 눌러야 하고, 한 화면에 펼치면 스크롤에서 지친다.
그래서 **묻는 것이 같은 문항끼리 한 화면**이다. 척도가 화면마다 하나라
보기 읽는 법을 다시 익히지 않아도 된다.

| 상품 | 화면 수 | 순서 |
|---|---|---|
| BASIC | 6 | 해보고 싶은 일 · 해본 적 있는 일 · 내가 정한 것 · 일하는 방식 · 더 배우고 싶은 것 · 진로 맥락 |
| STANDARD | 8 | 위에 더해 해보고 싶은 일(2/2) · 보여 줄 수 있는 사례 |
| PRO | 9 | 위에 더해 과제를 맡아 본 정도 |

**같은 것을 묻는 문항은 어느 묶음에 있든 한 화면에 모은다.** 규격의 묶음
순서대로만 자르면 '해보고 싶은 일' 이 두 번, '진로 맥락' 이 세 번 나와서
응시자가 같은 데를 또 도는 줄 안다. 열여섯을 넘기면 그때만 나누고 `(1/2)`
를 붙인다.

**점수에 들어가지 않는 맥락 문항은 한 화면에 모은다.** 구성개념대로 쪼개면
한 문항짜리 화면이 네 번 나온다.

문항마다 바로 저장한다. 중간에 닫아도 `v2.html` 을 다시 열면 그 화면부터
이어진다.

## 3. 경험 입력을 검사 끝에 붙였다

마지막 화면에서 '다음' 을 누르면 채점을 끝내 놓고 경험 입력으로 간다.
**화면은 V1 과 같은 것을 쓴다**(`assets/evidence-ui.js`). 나가는 단추의 말만
다르다: 결과지에서 고치러 들어오면 '그만두기', 검사 흐름 한가운데서는
'지금은 건너뛰기' 다. 흐름 안에서 '그만두기' 라고 쓰면 검사를 접는 단추로
읽힌다.

건너뛰어도 결과는 나온다. 대신 결과지 맨 위에 무엇이 빠지는지와 '경험
추가하기' 가 붙고, 결정 표의 증거 칸이 '경험 미입력' 이 된다.

**경험을 적어도 다섯 값은 한 점도 바뀌지 않는다.** 관심·경험·결정 소유·
업무 방식·학습 의향은 문항에서만 나오고, 경험은 증거 준비도에만 붙는다.
`npm run v2:flow` 가 같은 응답으로 경험만 넣었다 뺐다 하면서 다섯 값의
JSON 이 글자 하나까지 같은지 본다.

**'경험 미입력' 과 '걸린 근거 없음' 을 가른다.** 적어 주셨는데 그 직무에
걸리는 신호가 없는 것과, 아직 안 적으신 것은 다른 상태다. 한 말로 적으면
적어 주신 분이 자기가 안 적은 줄 안다.

## 4. 결과지 첫 화면

**일곱 칸짜리 결정 표**다. 막대 그래프를 쓰지 않았다.

```
직무군 | 업무방식 | 관심 | 경험 | 학습의향 | 증거 준비도 | 지금 할 것
```

BASIC 6줄 · STANDARD 10줄 · PRO 16줄. 합산 칸이 없는 것은 일부러다. 여섯을
하나로 합치면 숫자 하나가 남고 그 숫자로는 무엇을 할지 알 수 없다. 관심이
높은데 경험이 없으면 지금 할 일은 지원이 아니라 작게 한 번 해보는 것이고,
그 말은 두 칸이 갈려 있어야 할 수 있다.

절은 상품마다 이렇게 는다.

| | BASIC | STANDARD | PRO |
|---|---|---|---|
| 절 | 6 | 8 | 10 |
| 더해지는 것 | | 무엇을 직접 정해 왔는가 · 내 경험이 어느 직무에 걸리는가 | 연구·과제를 어디까지 맡아 봤는가 · 서류·면접·포트폴리오로 가져갈 것 |

**왜 이 직무가 앞에 왔는지를 문항 번호로 되짚는다.** 가중치를 숨기지 않아서
"Q1, Q9, Q16 에 이렇게 답하셨습니다" 까지 적는다.

**학위는 묻는 장면과 읽는 법을 바꾸고 점수를 바꾸지 않는다.** 05절의 제목이
학부·석사·박사·학위 후 연구 경력으로 갈리고, 같은 답이면 점수는 같다.

## 5. 인쇄와 PDF

결과지 맨 위에 '인쇄 · PDF로 저장' 이 있다. `@media print` 에서 머리말·
단추·경험 입력 내비게이션을 걷어낸다. 브라우저 인쇄 대화상자의 'PDF로
저장' 이 그대로 파일이 된다. 서버가 없는 정적 플랫폼이라 PDF 를 서버에서
만들지 않는다.

## 6. 검사

```bash
npm run v2:check   # 채점·결정 규칙 (브라우저 없이)
npm run v2:flow    # 실제 브라우저로 끝까지 응시 19가지
```

`v2:flow` 가 보는 것은 규격이 요구한 열 가지 경우(학사 BASIC · 학사 PRO ·
석사 STANDARD · 박사 PRO · 포닥 PRO · 경험 미입력 · 경험 풍부 · 관심만 높음 ·
경험만 많음 · 상위 둘이 비슷함)와, 데이터가 섞이지 않는지, 합산 점수가
생기지 않았는지, 다음에 붙일 칸이 비어 있는 채로 준비돼 있는지다.

화면은 `docs/metri/shots/v2/` 에 있다. `node scripts/v2-shots.mjs` 로 다시
뽑는다.

## 7. 아직 안 한 것

- **조직 가치 다리.** `organization_context` · `value_path` ·
  `performance_evidence` 세 칸을 결과 JSON 에 만들어 두고 비워 뒀다.
  비워 두는 것과 없는 것은 다르다
- **나라별 층.** 목표 국가를 아직 묻지 않아서 늘 "자료가 없어 넣지
  않았다" 가 나간다
- **측정 오차.** 인지 면접과 파일럿 200명을 돌리기 전이라 숫자를 내지
  않는다. `measurement_error` 는 `null` 이고 그 자리에 왜 없는지를 적는다
- **상품 결제.** `v2.html` 은 세 상품을 화면에서 고르게만 한다. 결제와
  좌석에 붙이는 것은 PG 심사 다음이다

## 제출이 조용히 막히던 자리 (2026-10-05)

밖에 올려 두고 실제로 응시해 보니 **다 골랐는데 결과 쪽으로 안 넘어가는**
일이 났다. 화면에는 보기가 눌려 있고 위의 띠에는 `0/2` 가 적혀 있었다.

**응답은 DB 에 다 들어와 있었다.** 재현해 보니 저장은 멀쩡했고 갈린 것은
**띠의 수**다. 뒤로가기로 돌아오면 Next 가 앞서 그려 둔 쪽을 그대로
되살리는데(히스토리 이동은 늘 캐시를 쓴다), 그 쪽이 들고 있는 것은 **그때의
서버 상태**다. 그래서 응시자는 다 고른 화면을 보면서 덜 푼 숫자를 읽는다.

그 자체는 숫자가 늦게 따라오는 일이고, 사람을 막은 것은 그 다음이다.

- **다 풀었는가를 화면이 정하고 있었다.** 되살아난 쪽은 `initial` 이 비어
  있어 제출 단추가 잠겼다. 화면이 틀렸을 때 빠져나갈 길이 없었다
- **거절이 조용했다.** `submitAction` 이 거짓 하나만 돌려줬고 화면은
  `if (r.ok)` 뒤에 아무것도 하지 않았다. 누른 사람은 단추가 고장 난 줄 안다
- **어디가 남았는지 적지 않았다.** 띠에 묶음별 수가 있었지만 누를 수 없었다

고친 자리는 셋이다.

**다 풀었는가를 서버가 정한다.** 저장할 때마다 서버가 센 수를 같이 받고
(`saveAnswersAction` 이 `progress` 를 함께 돌려준다), 마지막 묶음의 단추는
잠그지 않는다. 눌러 보고 서버가 거절하면 그때 까닭을 적는다. **잠그는
판단이 화면에 있으면 화면이 틀렸을 때 길이 없다.**

**거절한 까닭을 값으로 돌려준다.** `submitV2` 가 `{ ok, reason, progress }`
를 돌려준다(`gone` · `already` · `incomplete`). 이미 닫힌 응시면 결과 쪽으로
보내고, 덜 풀었으면 **어느 묶음에 몇 개가 남았는지** 적고 그 자리로 가는
링크를 띄운다. 띠의 묶음 칩도 링크가 됐다.

**보낸 것만 지운다.** `flush` 가 끝나고 대기열을 통째로 비우고 있었다.
보내는 동안 고른 답이 그 자리에 들어와 있으면 **보내지도 않고 지워진다.**
지금은 보낸 열쇠 가운데 값이 그대로인 것만 지우고, 저장은 한 번에 하나만
보내며(겹치면 늦게 끝난 쪽이 먼저 끝난 쪽의 대기열을 지운다) 보내는 중에
더 생기면 끝나고 한 번 더 돈다.

**복구 사본을 읽는 코드가 없었다.** `localStorage` 에 적기만 하고 아무도
되살리지 않아서, 적어 둔 것이 쓰인 적이 없다. 들어올 때 한 번 읽어 아직
서버가 못 받은 답을 다시 보낸다. 쪽을 떠날 때도 한 번 더 보낸다.

**채점과 문항은 건드리지 않았다.** 바뀐 것은 저장하는 길과 다 풀었는가를
정하는 자리와 거절을 적는 자리뿐이다.
