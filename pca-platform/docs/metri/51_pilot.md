# 내부 결제 확인과 기계공학 파일럿

작성 2026-10-07. 검사와 채점과 결과지 구조는 이 회차에서 잠겼다. 여기 적은
것은 **사람을 들이기 전에 확인할 것과 그 순서**다.

열어야 하는 것과 열지 않는 것을 먼저 가른다.

| | 이 회차 | 까닭 |
|---|---|---|
| 내부 PG 확인 | 한다 | 돈길이 실제로 도는지는 눌러 봐야 안다 |
| 공개 유료 판매 | 열지 않는다 | 통신판매업 신고번호가 아직 없다 |
| 거래 메일 | 붙인다 | 결과지 안내가 안 가면 산 사람이 기다리다 들어온다 |
| 파일럿 20~30명 | 받는다 | 문항과 해상도 문제는 사람 자료로만 풀린다 |
| 검사 설계 수정 | 하지 않는다 | 파일럿 자료가 오기 전에는 근거가 없다 |

## 1. 운영 자리에서만 답하는 넷

볼륨이 붙어 있는지, 운영 DB 가 지속형인지, 복구가 실제로 되는지, 메일이
바깥으로 나가는지는 **그 컨테이너 안에서만** 답할 수 있다. 밖에서 돌리면
그 줄이 영원히 `UNKNOWN` 이다. 그래서 점검 명령을 운영 이미지에 같이
담아 두었다(`deploy/ops/package.json`).

Railway 에서 서비스를 고르고 오른쪽 위 메뉴의 Shell 로 들어가 차례로
돌린다.

```bash
npm run ops:check     # 열한 줄 — READY / WARNING / BLOCKED / UNKNOWN
npm run db:verify     # 핵심 표 · 외래키 · 중복 결제 제약
npm run pilot:check   # 파일럿 설문이 제대로 서 있는가
```

읽는 법은 이렇다.

- `PDF_VOLUME` 이 **READY** 여야 한다. `/app/var/reports` 에 1MB 를 쓰고
  되읽은 다음, `/proc/mounts` 에 제 줄로 서 있는지까지 본 결과다.
  `BLOCKED` 로 나오면 Railway 의 Settings 에서 Volumes 의 Mount path 를
  `/app/var/reports` 로 걸어 준다. 이 줄이 빨간 동안 결제를 받으면
  **다음 배포에 구매자의 PDF 가 전부 사라진다.**
- `DATABASE` 가 READY 이려면 `DB_IS_PERSISTENT=yes` 가 꽂혀 있어야 한다.
  바깥 호스트라는 것만으로는 지속형이라는 보장이 없어서, 사람이 한 번
  확인해 준 값을 본다.
- `APP_ENV` 는 파일럿 동안 `staging` 으로 둔다. 가짜 결제를 쓰는 길이
  열려 있어야 파일럿 참가자에게 돈을 받지 않고 유료 등급을 드릴 수 있다.
- 시연 자료가 섞여 있다고 적히면 공개 전에 걷어낸다. 막지는 않는다.

복구는 **운영 원본을 읽기만 하고** 임시 PostgreSQL 에 붓는다. 붓는 자리를
따로 받지 않으면 거절한다.

```bash
PLAN=1 DATABASE_URL=<운영> bash scripts/backup-restore.sh      # 아홉 걸음만 찍는다
DATABASE_URL=<운영> RESTORE_URL=<임시> bash scripts/backup-restore.sh
```

끝까지 돌면 그 자리에서 `site_settings` 에 기록이 생기고, `/admin/launch`
의 `BACKUP_RESTORE` 가 초록으로 돌아간다. 사람이 날짜를 적어서 통과시킬
수 있는 길은 없다.

## 2. 내부 결제 확인

### 받아야 하는 값

PortOne 콘솔에서 가져와 Railway 의 Variables 에 넣는다. **값을 이 문서나
저장소에 적지 않는다.**

| 변수 | 무엇 | 비밀인가 |
|---|---|---|
| `PAYMENTS_PROVIDER` | `portone` 으로 바꾼다 | 아니다 |
| `PORTONE_STORE_ID` | 상점 식별값 | 아니다 (브라우저로 나간다) |
| `PORTONE_CHANNEL_KEY` | 국내 카드 채널 | 아니다 |
| `PORTONE_API_SECRET` | V2 API secret | **비밀** |
| `PORTONE_WEBHOOK_SECRET` | 웹훅 시크릿 | **비밀** |
| `PORTONE_CHANNEL_KEY_GLOBAL` | 해외 카드 채널 | 아니다. 지금은 없어도 된다 |

**테스트 채널로 시작한다.** PortOne 은 채널 단위로 실채널과 테스트 채널이
갈리므로, 테스트 채널 키를 꽂으면 실제 청구 없이 같은 코드 경로가 돈다.
실채널로 한 건을 보려면 금액이 작은 상품으로 결제한 뒤 아래 환불까지 같은
자리에서 돌린다.

### 코드로 보는 것

```bash
npm run pg:smoke
```

돈을 한 푼도 움직이지 않고 여섯 자리를 센다. 다섯 값이 꽂혀 있는가, API
열쇠가 실제로 먹는가(없는 결제 번호를 한 번 조회해서 401 과 404 를 가른다),
웹훅 서명을 맞는 것과 틀린 것과 오래된 것으로 가리는가, 금액과 통화가
다르면 막는가, 돌아올 주소가 이 배포본인가, 같은 결제가 두 번 적히지 않게
제약이 서 있는가.

**승인을 내지 않는다.** 결제를 만드는 코드를 두면 그 코드가 언젠가 운영에서
돌아간다. 그래서 카드를 긁는 것은 사람이 한다.

### 사람이 눌러야 하는 한 건

1. 파일럿용 계정으로 로그인한 뒤 `/pricing` 에서 STANDARD 를 고른다
2. 결제창을 끝까지 눌러 완료 화면으로 돌아온다
3. 주문번호를 적어 둔다

그 뒤를 명령이 받는다.

```bash
npm run pg:confirm -- <주문번호>            # 확정 · 이용권 · 멱등
npm run pg:confirm -- <주문번호> --환불      # 되돌리기까지
```

보는 것이 셋이다. 대행사가 승인이라고 하는가, 우리 주문이 확정되고 이용권이
생기는가, **두 번 불러도 한 번만 적히는가.** 마지막이 중요한 까닭은 웹훅과
리다이렉트가 같은 순간에 들어오는 날이 있기 때문이다. 줄이 두 벌 앉으면
이용권도 두 개 나간다.

환불까지 돌리면 주문 상태가 `refunded` 로 바뀌고 장부에 줄이 남는다. 집행은
대행사가 하고 기록은 우리가 한다. 둘을 한 함수에 두면 송금이 실패한 날
장부에만 환불이 적힌다.

## 3. 거래 메일 연결

### 받아야 하는 값

| 변수 | 무엇 | 비밀인가 |
|---|---|---|
| `MAIL_HOST` | 대행사 SMTP 주소 | 아니다 |
| `MAIL_PORT` | 587 또는 465 | 아니다 |
| `MAIL_USER` | 계정 | 아니다 |
| `MAIL_PASS` | 비밀번호 또는 열쇠 | **비밀** |
| `MAIL_FROM` | `hari_info@hari.re.kr` (확정) | 아니다 |
| `MAIL_CHECK_TO` | 확인용으로 받아 볼 주소 | 아니다 |

`MAIL_FROM` 의 도메인은 이미 SPF 와 DMARC 가 서 있다. 보내는 도메인을
이름으로 재지 않고 DNS 로 확인한다(`src/lib/mail-domain.ts`).

### 확인

```bash
npm run mail:check
```

스물두 가지를 본다. 가짜 SMTP 로 아홉 갈래가 쌓이고 나가는 것을 먼저 보고,
자격증명이 있으면 **진짜 서버에 붙어 한 통을 실제로 보낸다.** 자격증명이
없으면 그 두 줄은 `막힘` 으로 끝난다. 초록으로 적으면 메일이 다 됐다고
읽히고, 그 상태로 켜면 가입한 사람이 먼저 안다.

**DKIM 은 밖에서 조회하지 않는다.** 셀렉터 이름을 대행사가 정하므로 없는
것을 없다고 적으면 멀쩡한 설정을 틀렸다고 말하게 된다. 한 통 보내고 받은
쪽 원문 헤더에서 `dkim=pass` 를 눈으로 확인한다.

## 4. 파일럿 운영 절차

### 누구를 몇 명

기계공학 전공 20명에서 30명. 학부 3학년 이상과 대학원생을 섞는다. 학위
단계가 결과를 바꾸지 않는 것은 코드로 확인됐으니, 섞는 까닭은 **읽는 사람의
처지가 다르기** 때문이다.

두 집단으로 가른다.

| 집단 | 몇 명 | 받는 것 | 묻는 것 |
|---|---|---|---|
| 무료 | 10~15 | BASIC 48문항, 본문 5장 | 여덟 가지 가운데 일곱 |
| 유료 | 10~15 | STANDARD 68문항 또는 PRO 92문항 | 여덟 가지 전부 |

**같은 분께 두 번 풀게 하지 않는다.** ME_V2 는 등급이 문항 수를 정해서
(48 · 68 · 92) 48문항을 푼 응시에 유료 절을 얹을 수 없고, 같은 분의 응답이
두 벌 쌓이면 앞으로 만들 규준이 오염된다. 그래서 등급 사이의 값 차이는
유료 집단에게 **유료에만 있는 부분이 값을 낼 만했는지**로 묻는다. 받은
사람이 답할 수 있는 물음만 묻는다.

### 한 사람이 지나는 길

```
모집 알림 → 가입 → (무료) 무료 BASIC 열기 / (유료) 결제 또는 이용권 받기
         → 응시 → 경험 입력(건너뛸 수 있다) → 결과지 → PDF
         → 설문 열여덟 문항
```

파일럿 동안 결과지 위에 `읽은 느낌 알려 주기` 가 뜬다. `PILOT_OPEN=yes`
일 때만 뜨고, 평소에는 손님 화면에 설문 단추가 서지 않는다. **설문으로
결과지를 막지 않는다.** 답하지 않아도 잃는 것이 없다.

유료 집단에게 돈을 받지 않으려면 `APP_ENV=staging` 에서 가짜 결제로 이용권을
드린다. 이때 참가자 화면에는 공개 전 배포본이라는 띠가 뜬다. 모집 알림에
시험 운영이라고 적어 두면 그 띠가 설명이 된다.

### 일정

| 날 | 할 일 |
|---|---|
| D-3 | 운영 자리 넷 확인(1절), 거래 메일 한 통 확인(3절) |
| D-1 | 모집 알림 보내기, 동의문 올리기, `PILOT_OPEN=yes` |
| D+0~D+7 | 응시와 결과지. 막힌 사람은 `/support` 와 `/admin/incidents` 로 본다 |
| D+8 | 안 끝낸 분께 한 번만 알림 |
| D+10 | 설문 마감, `PILOT_OPEN` 내리기 |
| D+11 | 집계와 판단(아래 중단 기준) |

### 받은 것을 보는 자리

`/admin/funnel` 이 파일럿 집계를 같이 그린다. 척도는 평균과 사람 수, 자유
입력은 적어 주신 글이다. **다섯 명 미만인 칸은 숫자를 내지 않고 적어 주신
글도 내놓지 않는다.** 네 줄짜리 표에서는 그 글이 누구 것인지 짐작이 되고,
그러면 익명이 아니다.

### 다음으로 넘어가는 선

파일럿 뒤에 무엇을 할지 **자료보다 먼저 적어 둔다.** 숫자를 보고 기준을
정하면 그 기준은 아무것도 막지 못한다.

| 묻는 것 | 넘어가는 선 | 못 넘기면 |
|---|---|---|
| 결과가 본인과 맞는지 | 5점 가운데 3.5 이상 | 문항과 가중치를 다시 본다 |
| 왜 그 직무가 나왔는지 이해 | 3.8 이상 | 근거 문항 인용을 늘린다 |
| 부족한 근거가 무엇인지 이해 | 3.8 이상 | 공백 설명을 다시 쓴다 |
| 다음 행동 실행 가능 | 3.5 이상 | 계획의 크기를 줄인다 |
| 이해하기 어려운 표현 | 같은 말이 셋 이상 지목되지 않음 | 그 말을 바꾼다 |
| 유료에만 있는 부분의 값 | 3.5 이상 | 등급 구성을 다시 본다 |

**멈추는 선도 적어 둔다.** 본인과 맞는지가 3.0 미만이거나, 전 영역 동점이
응답의 3분의 1을 넘으면 공개 판매를 열지 않고 문항부터 다시 본다. 뒤쪽은
역문항이 없는 것과 BASIC 의 직무 구분 해상도에 걸린 문제이고, 그 둘은
파일럿 자료가 있어야 고칠 수 있다.

### 개인정보

- 설문 자유입력은 **파기 대상**이다(`src/lib/erasure.ts`). 탈퇴하면 지운다
- 집계에 이름과 학번이 들어가지 않는다. 응시 번호로만 센다
- 동의문은 `/legal` 의 개인정보 처리방침을 그대로 쓴다. 파일럿용 문서를
  따로 만들지 않는다

## 5. 설문 열여덟 문항

고르는 문항 열에 적는 칸 여덟이다. 3분에서 5분쯤 걸린다. 비워 두셔도 된다.

| 차례 | 모양 | 문항 | 재는 칸 |
|---|---|---|---|
| 1 | 1~5 | 결과지에 적힌 것이 본인을 설명한다고 느끼셨습니까 | `fit` |
| 2 | 1~5 | 그 직무들이 왜 나왔는지 결과지만 읽고 설명할 수 있습니까 | `why` |
| 3 | 1~5 | 전에 생각해 보지 않은 직무를 결과지에서 보셨습니까 | `newrole` |
| 4 | 1~5 | 지금 어떤 근거가 부족한지 분명해졌습니까 | `gap_clear` |
| 5 | 1~5 | 결과지가 진로 결정을 분명하게 했습니까 | `clarity` |
| 6 | 1~5 | 적힌 다음 행동을 실제로 하실 수 있습니까 | `doable` |
| 7 | 1~5 | 결과지를 읽고 진로에 대한 판단이 달라졌습니까 | `changed` |
| 8 | 1~5 | 이 결과지에 값을 내시겠습니까 | `wtp` |
| 9 | 1~5 | 남에게 권하시겠습니까 | `recommend` |
| 10 | 1~5 | 유료에만 있는 부분이 값을 낼 만했습니까 (유료 집단만) | `tier_value` |
| 14 | 적기 | 새롭게 알게 된 직무가 있으면 그 이름 | `newrole_name` |
| 15 | 적기 | 먼저 살펴봐야 할 경로는 무엇이었습니까 | `paths` |
| 16 | 적기 | 가장 큰 증거 공백은 무엇이었습니까 | `gap` |
| 17 | 적기 | 다음에 무엇을 하시겠습니까 | `action` |
| 18 | 적기 | 어느 부분이 헷갈렸습니까 | `wording` |
| 19 | 적기 | 어느 부분이 가장 쓸모 있었습니까 | `useful` |
| 20 | 적기 | 얼마면 알맞다고 느끼십니까 | `price` |
| 21 | 적기 | 다시 쓰게 하려면 무엇이 있어야 합니까 | `again` |

받은 규격 §20 의 열 문항은 문면을 한 글자도 고치지 않았다. 물음을 바꾸면
다른 것을 재게 되고, 그러면 파일럿 결과를 규격과 견줄 수 없다. 더한 여덟은
이번에 반드시 받아 와야 하는 칸이고, 덮였는지는 `npm run pilot:check` 가
`pilot_items.topic` 으로 센다.

16·17·18 세 문항은 **이해를 되묻는 자리**다. 결과지를 읽은 분이 자기 말로
적을 수 있으면 읽힌 것이고, 적지 못하면 점수가 아무리 맞아도 전달되지 않은
것이다.

## 6. 아직 아닌 것

- 실제 PG 로 한 건도 결제하지 않았다. 열쇠가 들어오면 2절을 돌린다
- 메일을 바깥으로 한 통도 보내지 않았다. 코드 쪽은 스물두 가지가 선다
- 운영 볼륨과 지속형 DB 와 복구는 컨테이너 안에서 사람이 한 번 돌려야
  답이 나온다. 밖에서는 `UNKNOWN` 이고 그것을 초록으로 적지 않았다
