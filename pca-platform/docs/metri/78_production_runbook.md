# 78. 운영 런북 (정본)

> **이 문서가 정본이다.** 운영에 무엇을 하는지는 여기 적힌 차례를 따르고,
> 다른 문서는 **한 걸음의 자세한 내용**을 맡는다. 두 곳에서 따로 적으면
> 어느 날 갈리고, 갈린 날 둘 다 못 믿는다(설계 원칙 10 과 같은 까닭).
>
> 걸음마다 **PASS 와 FAIL 을 적어 두었다.** `돌려 본다` 로만 적으면 읽는
> 사람이 무엇을 보고 넘어갈지 모르고, 애매하면 넘어가는 쪽으로 읽는다.

## 0. 먼저: 이 기계에서 **확인할 수 없는 것**

저장소와 로컬 DB 로 되는 일과, 운영 컨테이너나 밖의 브라우저가 있어야
되는 일은 다른 일이다. 섞으면 **안 본 자리가 초록으로 선다.**

| 묻는 것 | 어디서 답이 나오는가 |
|---|---|
| 코드가 그렇게 짜여 있는가 | 이 기계 (`npm run v3:all` 등) |
| 복구가 되는가 | 이 기계 + 로컬 PostgreSQL (아래 5번) |
| 운영 DB 가 지금 코드까지 올라와 있는가 | **운영 컨테이너 Shell 뿐** |
| 운영 볼륨에 PDF 가 남는가 | **운영 컨테이너 Shell 뿐** |
| 실제 PG 로 결제가 되는가 | **사람이 카드로** |
| 실제 구글·애플 로그인이 되는가 | **사람이 브라우저로** |
| `app.careermatri.com` 이 지금 서 있는가 | **밖의 브라우저로** |

**아래 어느 줄도 `이 기계에서 통과` 를 `운영에서 통과` 로 바꿔 적지
않는다.** 운영 쪽 걸음은 `사람` 으로 표시해 두었다.

## 3. 운영 DB (**사람이 컨테이너에서**)

Railway → 서비스 → ⋯ → Shell.

| | 명령 | PASS | FAIL 이면 |
|---|---|---|---|
| 3-1 | `npm run db:verify` | 핵심 `7 / 7` · ME_V3 `5 / 5` · 내 CareerMatri `5 / 5` | 3-2 로 간다 |
| 3-2 | `npm run db:upgrade` | 종료코드 0 · `ERROR` 0건 | 로그의 첫 ERROR 를 읽는다. **두 번째 실행은 안전하다** |
| 3-3 | `npm run db:verify` 다시 | 위와 같다 | `db:chain` 이 가리키는 파일이 이미지에 들어왔는지 본다 |

**`db:upgrade` 가 정상 종료한 것은 다 올랐다는 뜻이 아니다.** 그 명령은
자기가 아는 파일만 붓는다. 모르는 파일은 실패할 기회조차 없다. 그래서
**판정은 늘 `db:verify` 가 한다.**

모든 psql 이 `--single-transaction` 이고 목록의 파일이 전부
`IF NOT EXISTS`·`ON CONFLICT` 다. `DROP`·`TRUNCATE`·`db:init` 은 이 길에
없다.

## 4. 운영 상태 (**사람이 컨테이너에서**)

| | 명령 | PASS | FAIL 이면 |
|---|---|---|---|
| 4-1 | `npm run ops:check` | 열두 줄에 `UNKNOWN` 0 · `BLOCKED` 0 | 줄마다 적힌 Railway 자리를 본다 |
| 4-2 | `npm run pg:smoke` | 여섯 자리 통과 | PG 열쇠와 채널을 본다 |
| 4-3 | `npm run pilot:check` | 통과 | 파일럿 문항이 안 올라갔다 |

**`UNKNOWN` 을 `BLOCKED` 와 섞지 않는다.** 개발 PC 에서는 값이 없는 것이
당연하고, 그것은 **운영이 비었다는 뜻이 아니라 내가 그 값을 안 들고 있다는
뜻**이다. 그래서 4번은 **컨테이너 안에서만** 답이 된다.

**컨테이너에 있는 명령은 여덟뿐이다**(`deploy/ops/package.json`). 저장소의
`package.json` 과 다르다. `Dockerfile` 이 그 파일을 `/app/package.json`
으로 덮는다. 저장소 파일을 읽는 검사(`oauth:ready` · `mail:check` ·
`launch:check`)는 **거기서 돌지 않으므로** 1번에 둔다. 그 가운데 환경변수만
보면 답이 나오는 것은 `ops:check` 가 한 줄로 맡는다: 소셜 로그인은
`OAUTH` 줄, 메일은 `EMAIL` 줄이다.

## 5. 복구: 되돌릴 수 있는가

이 기계에서도 되지만 **운영 DB 를 받는 쪽은 사람이 한다**.

| | 명령 | PASS | FAIL 이면 |
|---|---|---|---|
| 5-1 | `PLAN=1 bash scripts/backup-restore.sh` | 아홉 걸음이 찍힌다. **아무것도 실행되지 않는다** | — |
| 5-2 | `RESTORE_URL=<임시> bash scripts/backup-restore.sh` | 표 열넷의 줄 수가 같다 · 제약 열 가지 · 외래키 개수 같음 · 굳은 결과 두 종류가 열린다 | 덤프가 반쪽이다. **그 백업은 백업이 아니다** |

**받는 쪽은 읽기만 한다.** 붓는 자리는 `RESTORE_URL` 로 따로 받고, 없으면
운영처럼 보이는 주소를 **거절한다**(`SAME_SERVER=1` 로만 뚫린다).
`READ_ONLY=1` 이면 기록도 남지 않고, 그러면 `launch:check` 의 백업 줄은
그대로 막힌 채다. **사람이 날짜를 적어서 초록을 만들 수 없다.**

세는 표가 열넷인 것이 중요하다. 한동안 아홉이었고 **그 아홉이 전부
ME_V1·V2 때의 것**이어서, 지금 파는 판본의 응시와 결과와 지금 상태가
통째로 안 돌아와도 `줄 수가 같다` 가 찍혔다.

## 10. 이 문서를 지켜 주는 장치

`npm run runbook:check` 가 센다.

- 여기 적힌 `npm run <이름>` 이 **전부 `package.json` 에 있는가**.
  없는 명령을 적어 두면 읽는 사람이 `Missing script` 를 받고, 한 번
  실제로 그랬다(`db:v3:arch` 를 운영 안내에 적어 두었는데 운영 이미지의
  `package.json` 에는 없었다)
- 걸음마다 **PASS 와 FAIL 칸이 비어 있지 않은가**
- 9절이 가리키는 문서가 **실제로 있는가**
