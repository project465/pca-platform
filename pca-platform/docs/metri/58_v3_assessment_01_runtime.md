# 58-1. Runtime 과 저장과 등급

## Runtime 이 하는 일

받는 것은 응시 하나의 상태다: 사용자 · 등급 · 학위 단계 · 전공계열 ·
지금까지의 응답 · routing 결과. 돌려주는 것은 **지금 보여 줄 화면 하나**다.

```
openAttempt → recomputeRouting → buildPlan → viewOf(화면 하나)
                                      ↓
                                  saveAnswer / savePicks
                                      ↓
                                  submit → scoring/engine → v3_snapshots
```

`src/lib/me-v3/runtime/` 넷이 전부다.

| 파일 | 하는 일 |
|---|---|
| `routing.ts` | 어느 영역을 선별하고 어느 영역을 깊게 볼지 |
| `blocks.ts` | 화면 묶음. 무엇을 어떤 차례로 묻는가 |
| `progress.ts` | 어디까지 왔는지. 두 수준 |
| `session.ts` | 응시 하나의 생애. 열기 · 저장 · 이어보기 · 등급 · 제출 |

**판정은 여기서 하지 않는다.** `submit` 이 `score()` 를 한 번 부르고
그 결과를 `v3_snapshots` 에 한 줄 적는다. 줄은 쌓이기만 하고 고치지 않는다.

## DB

`db/schema_v3_runtime.sql` 의 다섯 표다. **ME_V2 표를 쓰지 않는다**:
직무군 열여섯과 기술영역 열둘 사이에 1 대 1 사상이 없어서 섞으면 어느
쪽도 아닌 값이 나온다.

| 표 | 담는 것 |
|---|---|
| `v3_attempts` | 등급 · 학위 · 계열 · 열린 영역 · 고른 팩 · 지금 화면 · 판본 셋 |
| `v3_responses` | 응답. 종류와 값과 덧붙인 한 줄 |
| `v3_evidence_picks` | 축마다 고른 판단 체크리스트 · 산출물 · 검증 대상 |
| `v3_tier_events` | 등급을 올린 기록 |
| `v3_snapshots` | 그때 낸 판정과 판본 여섯과 응답 품질 |

**석사 이상은 계열 없이 시작되지 않는다.** 화면이 지키게 두지 않고
`CHECK (education_stage = 'bachelor' OR grad_field IS NOT NULL)` 가 막는다.
화면은 늘어나고, 늘어난 화면 하나가 빠뜨린다.

**이용권 하나가 응시 하나다.** `v3_attempts(entitlement_id)` 에 유일
인덱스가 있어서 같은 사람의 응답이 두 벌 쌓이지 않는다. 규준이 생기기
전에 오염되면 되돌릴 방법이 없다.

이번 회차에 칸 하나를 더했다. `v3_responses.note_text` 는 번역 단계에서
덧붙이는 한 줄이고 **응답이 아니다**: 고른 보기가 단계를 센 근거이고 이
줄은 결과지가 그 사람의 말로 옮겨 적을 때 읽는다. 줄만 적고 보기를
고르지 않았으면 그 문항은 아직 답하지 않은 것으로 남는다. 줄 하나로
단계가 섰다고 세면 번역 열 단계가 적는 사람에게만 유리해진다.

## Routing

영역 선별은 **Core 응답으로 먼저 확정된다.** 격자 서른여섯이 다 들어오면
경험 횟수와 관심으로 차례를 세우고, 선별 둘과 심화 셋을 고른다.
**산업이나 역할을 고른다고 심화 영역이 달라지지 않는다**(`v3:runtime` 에서
팩을 바꿔 가며 Core 판정이 글자까지 같은지 본다).

넷째 영역은 둘 중 하나일 때만 **추가 결제 없이** 열린다.

- `TIE_AT_THIRD` 3위와 4위가 같은 값이라 가를 수 없다
- `ALL_TIED` 열두 영역이 전부 같은 값이다

경험이 모자란 것은 넷째를 여는 까닭으로 쓰지 않는다. 그러면 **빈 영역을
하나 더 묻는 셈**이고, 응답은 늘고 확인되는 것은 늘지 않는다.

**심화 영역은 선별 네 축도 함께 받는다.** 이것이 구현 중에 나온 설계
구멍이었다. 선별에서 보지 않은 영역이 심화로 올라오면 여덟 축 가운데
넷만 답한 상태가 되고, 그 영역은 구조적으로 근거가 설 수 없다.

## 저장과 이어보기

응답은 **고른 자리에서 서버에 적는다.** 브라우저 저장소에 두면 기기를
바꾸는 순간 사라지고, 사라진 것을 응시자는 끝까지 모른다. 보기 하나는
작아서 문항마다 보내도 느려지지 않는다.

이어 들어오면 **마지막으로 보던 화면**이 열린다. 자리는 DB 에 화면
이름으로 남는다. 주소에는 몇째인가만 적는다: 화면 이름에 내부 코드가
들어 있어서 주소에 적으면 응시자가 그것을 본다.

**뒤로 가서 고칠 수 있다.** 격자를 고치면 뒤에 묻는 영역이 다시 정해진다
(`recomputeRouting`). 이미 답한 심화 응답은 지우지 않는다: 영역이 빠지면
채점에서 읽히지 않을 뿐이고, 되돌아오면 그대로 쓰인다.

## 등급 올리기

BASIC ⊂ STANDARD ⊂ PRO 라 **같은 응시의 등급을 올리고 추가 묶음만 연다.**
앞에서 답한 것은 그대로 쓴다.

```
BASIC 완료 → STANDARD 구매 → 새로 묻는 화면 17개 (응답 34)
STANDARD   → PRO            → 새로 묻는 화면 13개 (응답 15, 팩까지 27)
```

처음부터 다시 풀게 하면 그 사람은 두 번째 응답을 성실하게 하지 않고,
같은 사람의 응답이 두 벌 쌓여 규준이 오염된다.

올린 뒤에는 **새로 묻는 첫 화면**으로 옮긴다. 끝난 자리에 그대로 두면
더 풀 것이 없는 줄 안다(실제로 한 번 그렇게 짜서 PRO 로 올린 응시가
팩을 한 번도 고르지 못했다).

## 사람 다섯 벌이 끝까지 간다

`npm run v3:runtime` 이 실제 DB 로 돌린다.

```
P01 경험 거의 없는 학부생   BASIC     화면 33 · 응답 16 · 근거 없음 · LOW_VARIANCE
P03 캡스톤 학생           STANDARD  화면 57 · 응답 50 · 근거 세 영역 · OK
P04 구조해석 석사          PRO       화면 75 · 응답 67 · 근거 세 영역 · OK
P09 재료 박사            PRO       화면 75 · 응답 67 · 근거 두 영역 · OK
P12 경험 강한 포닥         PRO       화면 76 · 응답 68 · 근거 세 영역 · OK
```

P01 이 `근거 없음` 인 것이 맞는 결과다. 경험이 없다고 답한 사람에게
근거가 섰다고 적으면 그 결과지는 아무 말도 하지 않은 것이 된다.
