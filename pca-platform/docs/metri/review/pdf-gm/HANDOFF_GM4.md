## 1. 받은 지시 (Human Review, v3 승인 보류)

v3 는 RICH 50쪽 · POOR 47쪽 · CONTRA 53쪽이다. 분량과 기본 내용은 나아졌지만 상품 승인은 보류됐다.

1. **개인별 취업 전략의 연결 오류를 고친다.** RICH 5쪽에서 경영기획이 목표인 학생에게
   ‘지난 캠페인 반응’ 비교 과제가 섰다. POOR 에서는 마케팅 목표인데 고객 응대 기준 과제가
   지나치게 앞에 서고 되풀이됐다. 문구만 고치지 말고 사슬 전체를 전수 점검한다:
   `학생 목표 → 실제 검사 결과 → 확인된 Evidence → 탐색 직무 → 직무 요구사항 → 실행 과제 → 산출물`.
   실행 과제가 목표 직무에 직접 기여하는지, 다른 직무의 틀이 섞이지 않았는지 검증한다.
   직무 사이의 공통 역량을 쓸 때는 연결 이유를 분명히 적는다.
2. **한국어 문장을 고친다.** 다음을 없애거나 다시 쓴다: `기준을 두는지` · `그 판단을 받치는` ·
   `목표 직무와의 거리` · `가장 단단하게 확인된 부분` · `다음 과제에서 내가 정한 것으로 만들어 보면` ·
   `이 직무가 반드시 보는 판단`. 개발 쪽 말과 측정 모델 용어를 학생 문장에 쓰지 않는다.
   짧게 만들기보다 뜻을 정확하고 자연스럽게 전한다.
3. **전문 보고서 디자인.** 사용자가 준 Annual Report 레퍼런스의 편집 완성도가 기준이다.
   장 제목 옆에 작은 그림을 붙이는 정도로는 모자란다. 분석 · 기업 심층 · 실행 계획 쪽마다
   목적에 맞는 편집형 그래픽을 쓴다. 본문은 읽기 편한 크기로, 표는 덜 빽빽하게, 여백과 정렬은
   일관되게 둔다. 근거 자료가 없는 차트나 지표를 꾸미려고 만들지 않는다.
   **주의: Annual Report 레퍼런스 이미지는 이 세션에 첨부되지 않았다**(`/mnt/user-data/uploads`
   에는 reference-home 이미지뿐). 새 세션에서 사용자에게 다시 받거나, 받지 못한 사실을 적는다.
4. **대표 5쪽을 먼저 실제 PDF 로 만든다**(v3 와 나란히 견줄 수 있게): ① 표지 ② 개인 역량 분석과
   방사형 그래프 ③ Evidence 심층 분석 ④ 실제 기업·직무 심층 분석 ⑤ 개인별 취업 실행 로드맵.
   쪽마다 적용한 디자인 원칙과 v3 대비 바뀐 점을 적는다.
   **이 5쪽이 승인되기 전에는 50쪽 전체를 다시 뽑거나 디자인 완료를 선언하지 않는다.**
5. **보존한다**: 50쪽 보고서의 실질 분석 내용 · R35 안정화 · 측정·채점·taxonomy·DB 계약 ·
   기업 공식 원문 미검증 상태 · KODATA 외부 배포 권한 미확정 표시 · 다른 학과로 넓히지 않음 ·
   운영 PDF 연결과 Production 배포 금지. **이번 단계는 분량 확대가 아니라 분석 정합성과
   프리미엄 편집 디자인이다.**

## 3. 지금까지 한 것 (이 WIP 커밋)

1. `data/report-gm/biz-role-guide.json` — 직무 8개마다 두 가지를 더했다.
   - `practice` (J1~J8): 목표 직무의 말로 쓴 실행 과제 · 산출물 · 확인 질문. 학생 과제 수준
     (수업·팀 과제·동아리)이고 현업 경력을 전제하지 않는다.
   - `lens` (그 직무의 업무 영역 셋): 그 직무에게 이 영역이 무엇인지(연결 이유 `why`), 과제를
     영역 문장으로 쓸지 직무 문장으로 쓸지(`mode`), 과제 앞머리(`ctx`). 다른 직무가 중심인 영역
     (예: 마케팅의 TD09 고객·서비스 운영)은 `mode: "role"` 이라 응대 문장 대신 마케팅 과제가 선다.
2. `src/lib/me-v3/report-gm/guide.ts` — `Practice` · `Lens` 타입.
3. `src/lib/me-v3/report-gm/analysis3.ts` — `strategy3()` 를 새로 두고 `priorities3()` 는 그것을 부른다.
   - 관계 넷: `DIRECT`(목표 직무의 핵심 판단이 아직 없음) · `ROLE_DOMAIN`(목표 직무의 업무 영역) ·
     `GOAL_UNASKED`(목표 직무 영역인데 이번에 묻지 않음 → 경험 확인) · `SHARED`(직무 공통 역량, 연결 이유를 적는다).
   - 사슬에 걸리지 않는 빈자리는 버리지 않고 `outside` 로 따로 적는다(“이번 실행 전략에서 뺐다” + 쓰는 직무).
   - 같은 과제를 두 번 세우지 않고, 직무 말로 쓴 과제는 같은 판단을 한 번만 세운다. 중심 영역은
     셋까지, 나머지 영역은 하나씩. 읽는 차례는 핵심 판단 → 중심 영역 → 경험 확인 → 공통 역량.
   - 목표 직무 밖에서 같은 판단을 해 봤으면 그 경험을 옮겨 쓸 수 있다는 연결 이유를 `why` 에 적는다.
   - 행마다 `chain`(목표 · 결과 · 근거 · 직무 요구 · 과제 · 산출물)을 든다 — 전수 점검표의 재료.
   - 도우미: `asTodo()`(‘~합니다’→‘~하기’), `l2Work()`(‘~를 정했다’→‘~를 정하는 일’),
     `dimWork()`(산업팩 ‘~를 두는가’→‘~를 정해 두는 일’, 지시 2번의 `기준을 두는지` 뿌리).
   - `npx tsc --noEmit` 통과.

이 로컬 DB 에서 돌린 새 결과(요약):

- RICH 경영기획: ① 경영전략·기획 · 목표를 지표로 옮기기 ② 재무·투자 판단(이번에 묻지 않음) · 추정 가정 정하기
  ③ 데이터·의사결정 · 넣고 뺄 자료 기준. 마케팅 비교는 `outside` 로 빠졌다.
- POOR 마케팅: ① 고객 구분·채널 배분 ② 채널 반응 비교 ③ 기획서 ④ 데이터·의사결정(묻지 않음) ⑤ 고객 문의·후기·불만을
  근거로 반응이 낮은 까닭 좁히기(응대 문장이 아니라 마케팅 과제). 고객 응대 기준 과제는 사라졌다.
- CONTRA 인사: ① 인사·조직 · 직무 요건 옮기기 ② 운영·프로세스 · 요건 옮기기 ③ 인사·조직 · 볼 기준과 배치 정하기.
  고객·서비스 운영 · 영업 · 회계 빈자리 다섯은 `outside`.

## 5. 새 세션에서 막힐 자리

- **검토 사례 데이터가 새 컨테이너에 없다.** RICH 462 · POOR 463 · CONTRA 464 는 이 세션의 로컬 PostgreSQL 에만
  있고, 그 원본(응시 74 · 431)도 마찬가지다. 굳은 결과를 저장소 파일로 떠 두려 했지만 이 세션의 권한
  검사가 DB 내용을 파일로 내보내는 것을 막았다. 새 세션은 둘 가운데 하나를 한다:
  (a) `npm run dev:setup` 으로 빈 DB 를 세운 뒤 `scripts/lab/gm-cases.ts` 를 고쳐, 원본 응시 대신 사람 셋의 규칙
  (`scripts/_v3-answer.ts`)으로 BIZ 응시를 만들어 RICH·POOR·CONTRA 를 다시 굳힌다(목표 직무: 경영기획 · 마케팅 · 인사).
  (b) 사용자가 허락하면 이전 세션 방식대로 fixture 파일을 만든다.
  어느 쪽이든 새 사례의 응시 번호와 결과가 v3 와 같지 않을 수 있다는 것을 보고에 적는다.
