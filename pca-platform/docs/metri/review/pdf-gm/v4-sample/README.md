# BIZ PDF GOLD MASTER v4 — 대표 5쪽 Human Review 요청

v3(RICH 50 · POOR 47 · CONTRA 53쪽)의 승인 보류 지시를 받아 **분석 정합성(실행 전략 사슬)과 학생 문장을 고치고, 대표 5쪽만 새 편집으로
뽑았다.** 50쪽 전체는 다시 뽑지 않았다: 이 다섯 쪽이 승인된 뒤에 뽑는다. 운영 PDF 에 연결하지 않았고 Production 에 배포하지 않았으며
다른 학과로 넓히지 않았다. **자동 검사 통과는 상품 품질 승인이 아니다.**

## 2. 실행 전략 사슬 (지시 1)

v3 는 결과 모델의 빈자리 순위를 그대로 실행 과제로 옮겨, 목표 직무와 무관한 영역의 말이 과제에 섰다. v4 는 사슬을 **목표 직무에서
거꾸로** 세운다(`strategy3()`): 목표 직무 → 그 직무의 업무 영역과 핵심 판단 → 그 자리의 실제 응답 → 목표 직무의 말로 쓴 과제 → 산출물.
걸리지 않는 빈자리는 버리지 않고 ‘이번 실행 전략에 넣지 않은 판단’ 표로 따로 적는다.

| 사례 | 목표 | v3 에서 틀린 자리 | v4 실행 전략 (차례대로) |
|---|---|---|---|
| RICH | 경영기획 | 60일 ‘지난 캠페인 반응’ 비교(마케팅 영역) | ① 경영전략·기획 · 목표를 숫자로 재는 지표로 옮겨 적기 ② 재무·투자 판단 · 추정에 쓸 가정을 정해 적어 두기 ③ 데이터·의사결정 · 무엇을 넣고 뺄지와 집단을 나누는 기준을 정하기 — 마케팅 비교는 ‘넣지 않은 판단’ 으로 |
| POOR | 마케팅 | 고객 응대 기준 과제가 맨 앞에 서고 요약·30일·마지막 할 일에 되풀이 | ① 고객 구분과 채널 배분 ② 채널·메시지 반응 견주기 ③ 캠페인 기획서 ④ 데이터·의사결정 · 자료 기준(묻지 않은 영역) ⑤ 고객 문의·후기·불만으로 반응이 낮은 까닭 좁히기(응대 문장이 아니라 마케팅 과제) |
| CONTRA | 인사 | 고객·서비스 운영 과제, 30일 응대 기준 · 60일 제안서 · 90일 영업 프로젝트 | ① 인사·조직 · 필요한 사람을 할 수 있어야 하는 일로 옮기기 ② 인사·조직 · 볼 기준과 배치 정하기 ③ 운영·프로세스 · 일의 순서와 역할 배분 — 90일은 엠티지 인사 프로젝트 |

이 표가 다른 장에도 그대로 이어진다: 종합 의견 ‘먼저 채울 부분’ · 한눈에 보기 ‘먼저 할 일’ · 실행 계획 30·60일 · 마지막 할 일 ·
면접 준비 질문(목표 직무 역할팩 문항에서 같은 판단을 묻는 것) · 90일 프로젝트(깊게 본 기업의 목표 직무 일, 없으면 목표 직무 안내의
첫 프로젝트) · 기업 심층의 직무 차례(목표 직무가 먼저). 실행 전략 장(06)에는 행마다 관계 이름표와 연결 이유, 사슬 다섯 칸(지금 응답 →
직무에서 필요한 것 → 할 일 → 남길 것)이 선다. 목표 직무 영역이 아닌 영역 해설(03장)의 ‘다음에 할 일’ 에는 실행 전략에 넣지 않았다는
한 줄이 붙는다.

인수인계 문서 4-1 의 다듬기 셋도 닫았다: J2 꼬리말(‘지표마다 재는 방법’ → ‘옮긴 조건마다 무엇으로 확인할지’) · 인사의 운영·프로세스는
처리 시간 지표가 아니라 역할 배분부터(`lens.axes`) · 재무·투자 가정 행에 ‘기준과 배분 정하기’ 대신 영역의 일을 행 제목으로
(‘추정에 쓸 가정을 정해 적어 두기’)와 그 일에 맞는 산출물(‘추정 가정과 근거 메모’, `lens.out`).

## 3. 학생 문장 (지시 2)

지시에 적힌 여섯과 같은 결의 측정 쪽 말을 뿌리에서 고쳤다. 세 사례의 렌더 결과 전체에서 0곳이다(`LINKAGE_AUDIT.md` 마지막 줄).

| 전 | 후 |
|---|---|
| 산업 판단 이름 `…기준을 두는지` (`askNoun`) | `…기준을 정해 두는 일` (`dimWork`) |
| 그 판단을 받치는 체크리스트 항목(근거 항목) | 체크리스트에서도 그 장면을 골랐습니다 / 체크리스트에서 고른 항목 |
| 목표 직무와의 거리 | 목표 직무 준비 상태 |
| 이번 결과에서 가장 단단하게 확인된 부분 | 이번 결과에서 가장 분명하게 확인되는 판단 |
| 다음 과제에서 … ‘내가 정한 것’으로 만들어 보면 좋습니다 | 다음 과제에서 … 기준까지 직접 정해 보면, 지원서에서 ‘내가 정한 일’로 말할 수 있게 됩니다 |
| 이 직무가 반드시 보는 판단 | 이 직무의 핵심 판단 |
| 판단 문항 · 단계로 답함 | 판단을 묻는 질문 · 스스로 해 봤다고 답함 |

검사 줄: `scripts/lab/gm-linkage.ts` 의 `BANNED` 가 렌더한 리포트 전체의 글자에서 센다.

## 4. 바꾸지 않은 것

측정 · 채점 · 문항 · taxonomy · DB 계약 · 결과 모델 · R35 안정화 화면. `npm run v3:freeze:measure` 가 기록을 다시 적지 않은 채로
14/14 통과. 기업 공식 원문 직접 확인 0건 · KODATA 학생 배포 권한 미확정 · 채용 여부 미확인 표시는 그대로다. 운영 PDF 경로
(`/v3/{id}/result/pdf`)와 Production 은 건드리지 않았다.

## 5. 이 컨테이너의 제약과 대신한 것 (사실대로)

- **npm 레지스트리 · GitHub 내려받기가 네트워크 정책으로 막혀 `npm ci` 가 되지 않았다.** 그래서 저장소 밖(세션 scratch)에 임시 실행기를 두고
  저장소 코드를 그대로 돌렸다: 전역 TypeScript 로 `.ts` 를 옮겨 실행하고, `pg` 는 PyPI 의 psycopg 로 붙는 대체 모듈, `bcryptjs` 는 로컬
  검토용 계정에만 쓰는 대체(이 계정으로 로그인하지 않는다). `dev:setup` · `db:upgrade` · `gm-cases2` · `gm-linkage` · `gm-sample4` ·
  `v3:freeze:measure` · `secrets:check` · `claims:check` 는 이 실행기로 돌렸다. 저장소에는 임시 실행기를 넣지 않았다.
- **`npx tsc --noEmit` 은 돌리지 못했다**(`node_modules` 와 `@types` 없음). 대신 전역 `tsc` 로 바뀐 파일(`report-gm/*` · `gm-*.ts`)을
  외부 모듈만 임시 선언으로 바꿔 검사했고 고친 파일에서 난 오류는 0이다. 저장소의 정식 `npm run typecheck` 는 의존성이 설치된 곳에서 한 번
  더 돌려야 한다.
- **글꼴**: 처음에는 Pretendard 를 받을 수 없어 NanumGothic 으로 뽑았다. 2026-10-20 에 GitHub 릴리스 내려받기가 열려 Pretendard 1.3.9 공식 배포본(GitHub `orioncactus/pretendard` 릴리스 zip · SIL OFL 1.1)으로 다시 뽑았다. 글꼴 파일은 저장소에 넣지 않고 `var/pdf-gm/fonts/pretendard/`(gitignore)에 둔다.
- **Annual Report 레퍼런스 이미지 없음**: `DESIGN_NOTES.md` 첫 절.
- **검토 사례**: 인수인계 문서 5절 (a) 방법으로, 빈 DB 에서 `gm-cases2.ts`(원본 응시 없이 사람 셋의 규칙으로 BIZ 응시를 만든다)로 다시
  굳혔다. v3 의 462 · 463 · 464 를 만든 스크립트가 이것이라 `gm-cases.ts` 를 고칠 필요가 없었다. 새 응시 번호는 1 · 2 · 3 이고, 실행 전략
  결과가 인수인계 문서 3절에 적힌 v4 WIP 결과와 같았다.

## 7. 아직 남은 것

- 이 다섯 쪽의 사람 판정. 승인 전에는 50쪽 전체를 다시 뽑지 않는다.
- 승인되면: 같은 편집 체계로 13~14장 전체를 다시 짜고 세 사례를 뽑는다(`render4.ts` 를 장 전체로 넓힌다).
- **CONTRA 의 고객·서비스 운영 경험을 인사 직무에 잇는 문장은 넣지 않았다(2026-10-20 지시 4).** 실제 근거를 되짚으니 모자랐다:
  응시 3 은 고객·서비스 운영(TD09)에서 일곱 축을 응답으로 확인했지만 **체크리스트에서 고른 항목이 0개**이고(응답 품질 `REVIEW` ·
  `CHECKLIST_MISMATCH_HIGH`), 경험 기록 ‘학생회 행사 운영 — 참가자 접수와 인원 배치’ 의 결정(‘볼 기준을 정했다’)은 인사·조직
  쪽 항목이다. 고객 응대 경험이 사람을 고르고 배치하는 판단으로 옮겨 간다는 것을 받치는 학생 근거가 없다.
  그리고 이 확인 중에 **이미 들어가 있던 억지 연결을 찾아 걷었다**: 실행 전략의 ‘다른 영역에서 확인된 같은 판단을 옮겨 쓴다’ 줄이
  응답만으로 확인된 축(고른 항목 없음)에서도 섰다. 지금은 **그 축의 체크리스트 항목을 실제로 고른 영역**에서만 그 줄을 세우고
  (`analysis3.ts` `transfer()` · `pickedIn`), 세 사례에서 그 줄이 0곳이다. RICH 대표 5쪽은 이 변경으로 한 글자도 바뀌지 않았다
  (쪽 그림 다섯의 지문이 같다).
- Annual Report 레퍼런스 쪽 그림을 받아 정보 위계 · 그래프 크기 · 본문 가독성 · 그림 구성 · 정렬 · 박스 디자인을 견준다.
- Pretendard 판에서 눈으로 찾아 고친 자리(2026-10-20 · 측정·채점 변경 없음): ① 2쪽 방사형 그림 안의 단계 눈금 글자가 선과 겹쳤다 → 그림 밖
  범례 한 줄(안쪽·가운데·바깥 고리)로 옮겼다 ② 5쪽 과제 칸 ‘남길 것 …’ 줄이 접힐 때 줄 사이가 벌어졌다(10pt 줄 위의 인라인 글자) → 블록으로 세웠다
  ③ 3쪽 여덟 단계가 8칸으로 좁게 서서 한 칸이 네댓 줄로 접혔다 → 4칸 × 2줄 ④ 4쪽 직무 업무 차례 세 칸이 좁아 네 줄로 접혔다 → 한 줄씩
  ⑤ 5쪽 프로젝트 이름에 따옴표가 겹쳤다(‘…'…'…’) → 이미 따옴표가 있으면 바깥 따옴표를 붙이지 않는다 ⑥ 자료의 ASCII 따옴표를 그리는 자리에서 ‘ ’ 로.
  남은 높이 19 · 87 · 4 · 120 · 153px(3쪽은 빠듯하다).
- 정식 의존성 환경(`npm ci` 가 되는 곳)에서 `npm run typecheck` 와 회귀(`v3:all` · `v3:freeze:measure`)를 다시 돌린다.
