# API_CONTRACT_REVIEW — 응시 저장 동작의 `{ ok: false }` (3차 Track C)

기준 커밋 `55b20bfb` · 작성 2026-10-20 · 범위: ME_V3 응시 화면의 서버 동작
(`src/app/v3/[attemptId]/actions.ts`) 일곱 가지와 그 유일한 소비자
(`src/app/v3/[attemptId]/screen.tsx`).

**판정: 공통 API 계약 변경에 해당한다.** 반환 꼴(`{ ok: boolean }`)은 그대로지만,
2차와 3차에서 **`ok: false` 가 나올 수 있는 경우가 늘었다.** 그래서 지시
(작업 2) 대로 **총괄 PM 승인 전 운영 병합 금지**로 묶는다. 같은 회차에 고친
`submit()` 의 연결 고갈(아래 1-2)은 계약을 바꾸지 않는 내부 수정이라 커밋을 따로
갈랐다.

## 1. 무엇이 바뀌었나

### 1-1. 서버 동작이 거짓을 돌려주는 경우

| 동작 | 55b20bfb 이전(1차) | 2차(`55b20bfb`) | 3차(이 회차) |
|---|---|---|---|
| `answerAction` | 남의 응시 · 끝난 응시면 `false`, 아니면 늘 `true` | **+ 제출과 겹쳐 `writable()` 이 물러나면 `false`** | 같음 |
| `picksAction` | 같음 | **+ 같음** | 같음 |
| `noteAction` | 늘 `true` | 늘 `true` (경합 뒤에도 씀) | **+ 끝난 응시에는 쓰지 않고 `false`** |
| `profileAction` | 늘 `true` | 늘 `true` (경합 뒤에는 0줄 갱신인데 `true`) | **+ 바뀐 줄이 없으면 `false`** |
| `picksAction3` | 던지면 `false`, 아니면 `true` | 같음 (0줄 갱신인데 `true`) | **+ 바뀐 줄이 없으면 `false`** |
| `cursorAction` | 화면 번호가 없으면 `false` | 같음 (끝난 응시의 자리를 덮음) | **+ 끝난 응시면 `false`, 자리를 덮지 않음** |
| `finishAction` | 남의 · 끝난 응시면 `false` | 같음 | 같음 (내부만 고침, 1-2) |

**반환 꼴은 한 글자도 바뀌지 않았다**: 여전히 `{ ok: boolean }` 하나이고 칸을 더하지
않았다. 바뀐 것은 **언제 `false` 가 나오는가**다.

### 1-2. 계약을 바꾸지 않은 내부 수정 — 제출이 연결을 못 얻던 자리

`submit()` 이 연결 하나로 응시 줄을 `FOR UPDATE` 로 잡은 채, 응답과 근거를 **풀의 다른
연결**로 읽었다. 같은 응시에 저장이 몰리면 그 저장들이 연결을 쥔 채 이 잠금을 기다리고,
제출은 읽을 연결을 못 얻어 10초 뒤 `timeout exceeded when trying to connect` 로 떨어졌다.
**학생 열넷이 같은 순간 제출하면 일곱이 떨어졌다**(아래 4절, 실제 node-postgres · 풀 10).
읽기를 그 트랜잭션의 연결로 옮겼다(`attemptOf` · `answersOf` · `picksOf` ·
`submissionOf` 가 연결을 인자로 받는다, 없으면 전과 같다). 반환값과 화면 동작은 그대로다.

## 3. 클라이언트 오류 처리

### 3-1. 고친 것 (명백한 버그)

`push()` 가 서버가 거절해도 머리띠에 **`저장됨`** 을 적었다. 반환값을 보지 않고
`.then(() => setSent(true))` 였기 때문이다. 3차에서 `{ ok: false }` 도 실패로 세어
`저장 실패 · 다시 시도` 를 띄우고, 누르면 같은 호출을 다시 보낸다
(`ME_V3_2_ASSESSMENT_UI_V45`, 검사 화면 동결을 다시 적었다 · 문항·보기·저장 값·문면 그대로).

### 3-2. 남은 것 (승인 요청 · 아직 고치지 않음)

| 상황 | 지금 화면 | 문제 | 제안 |
|---|---|---|---|
| 다른 탭에서 이미 제출했다 | `저장 실패 · 다시 시도` | 다시 눌러도 계속 실패한다. 까닭을 말하지 않는다 | `ok:false` 에 까닭 하나(`reason: "submitted"`)를 더하고 `제출이 끝난 검사입니다 · 결과 보기` 로 잇는다 — **반환 꼴에 칸을 더하는 일이라 별도 승인** |
| 연결이 잠깐 끊겼다 | 던짐 → 실패 · 다시 시도 | 정상 | — |
| 남의 응시 번호 | `ok:false` → 실패 | 정상(아무것도 안 쓰인다) | — |

문구를 고치는 일(`ASSESSMENT_COPY_VERSION`)과 반환 꼴을 넓히는 일은 이 회차 범위 밖이라
제안만 적는다.

## 4. 경합 증거 (실제 PostgreSQL · 실제 node-postgres 8.16.3)

보낸다. 그다음 제출 뒤에 같은 22번을 하나씩 다시 보낸다. 마지막으로 학생 N 명(풀 10 보다

## 5. HTTP 상태

| 경우 | 응답 | 화면 |
|---|---|---|
| 동작이 `{ok:true}` / `{ok:false}` 를 돌려줌 | **200** (Next 서버 동작은 반환값을 RSC 본문에 담는다) | 반환값으로 가른다 |
| 동작 안에서 던짐(DB 끊김 · 연결 시간 초과) | **500** · 클라이언트 promise reject | `push()` 의 두 번째 갈래 → 실패 |
| 로그인 만료(`requireUser` → redirect) | 303 → 로그인 | 화면이 이동 |
| 배포 뒤 옛 탭의 동작 ID | 404 `Server action not found` → reject | 실패 · 다시 시도(새로 고침하면 풀린다) |

**`ok:false` 를 4xx 로 바꾸지 않았다.** 서버 동작에는 상태 코드를 고를 자리가 없고, 바꾸려면
라우트 핸들러로 옮겨야 한다 — 그것이 더 큰 계약 변경이다.

## 6. 하위 호환성

- **반환 꼴이 같다**: 새 칸이 없어 옛 소비자 코드가 깨지지 않는다.
- **옛 탭**: 배포가 바뀌면 서버 동작 ID 가 바뀌어 옛 번들은 `Server action not found` 로
  던진다. 옛 `push()` 도 던진 것은 실패로 센다 → `저장 실패 · 다시 시도` · 새로 고침.
  **옛 번들이 새 서버의 `ok:false` 를 `저장됨` 으로 보는 길은 없다**(ID 가 같은 배포 안에서만
  맞기 때문이다).
- **저장된 응답의 뜻이 같다**: 스키마 · 값 · 문항 · 채점이 그대로다. migration 이 필요 없다.
- **측정 동결 `ME_V3_MEASUREMENT_FREEZE_1`** 이 기록을 다시 적지 않은 채로 통과한다.
- **바뀌는 사용자 체감**: 다른 탭에서 제출한 뒤 남은 탭에서 고르면 전에는 `저장됨` 이었고
  지금은 `저장 실패 · 다시 시도` 다. 전의 `저장됨` 이 거짓이었다.
