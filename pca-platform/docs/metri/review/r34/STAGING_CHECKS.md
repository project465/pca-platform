# R34 · Staging 에서 직접 확인하는 법

Staging 주소: `https://charming-reverence-staging.up.railway.app`

이 세션의 컨테이너는 그 주소에 닿지 못한다(네트워크 정책이 `*.up.railway.app` 을 막는다 · HTTP 000). 그래서 아래는 **사람이 Staging 에서 누르고 읽는 차례**이고, 이 문서의 모든 "기대값" 은 이 기계에서 같은 빌드로 재현한 값이다.

## 0. 먼저: 배포가 이 커밋인가

Railway → `staging` 환경 → 서비스 → Deployments 의 맨 위 커밋이 이 가지의 최신 커밋(아래 보고의 커밋 해시)인지 본다. 아니면 Redeploy 를 누르고 끝날 때까지 기다린다. 그다음 Shell 에서:

```
npm run ops:check        # 열한 줄. DEPLOY 줄의 커밋이 같은가
npm run db:verify        # 7 / 7 · 5 / 5 · 5 / 5
```

## 1. 응답 109 · 근거 8 이 실제로 저장됐는가 (읽기만)

그 학생의 결과 주소 `/v3/<응시번호>/result` 의 숫자를 들고 Shell 에서:

```
psql "$DATABASE_URL" -v att=<응시번호> -f /app/db/checks/v3_attempt_trace.sql
```

일곱 표가 선다. 보는 것: 2절 `응답 전체` = 109 · 3절 `고른 근거 전체` = 8 · 4절 굳은 결과가 **한 줄** · 6절 여덟 줄 전부 `in_result_model = t` 또는 `f` (f 면 그 항목은 확인에 못 미친 고른 항목이고, 결과지 영역 카드의 `골랐지만 응답으로는 아직 확인되지 않은 것` 줄에 선다). **쓰는 문장이 한 줄도 없다.**

## 3. 담당자 계정으로

`/org/v3` 와 `/org/v3/students` 가 그 학생을 센다(R33 과 같다). 이 회차에 담당자 화면은 바뀌지 않았다.

## 4. 종이(PDF)가 마지막 쪽을 거의 비운 채로 나오지 않는가

`/v3/<id>/result/pdf` 는 그 종이 하나에 대고 맞춘다. 그대로 뽑은 것에서 쪽 수를
세고, 글을 6% 안에서 줄여 쪽이 하나 줄어드는 첫 배율이 있으면 그것을 쓴다
(`src/lib/me-v3/result/pdf.ts` 의 `fitTail`). 담긴 글을 덜어내지 않고, 쪽이 줄지
않으면 1.0 그대로다.

- 확인: 학생 계정으로 PDF 를 받아 마지막 쪽을 연다. 마지막 쪽이 절반 아래로 비어
  있으면 FAIL. 로컬 감사 19벌(개인 ME 세 등급 + 학교 PRO 16벌)은 마지막 쪽이
  83~97% 다.
- 로그: `[v3-pdf] done attempt=<id> <bytes>바이트 <ms>ms` 한 줄. `Printing failed`
  가 적히면 브라우저가 인쇄 중에 닫힌 것이고 재배포 전 코드다.
- 학교 종이는 9~10쪽이 정상이다(부록의 여덟 축 목록을 종이에서 접었다). 13쪽을
  넘으면 FAIL.
