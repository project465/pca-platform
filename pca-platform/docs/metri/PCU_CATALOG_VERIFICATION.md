## E. 코드 호환성

**한 번 쓴 코드가 다른 학과를 가리키면 안 된다.** 그렇게 두면 그 코드로
적힌 지난 응시 줄이 조용히 남의 학과 줄이 되고, 담당자 화면과 집계가
틀린 이름으로 맞게 생긴 숫자를 낸다.

그래서 뜻이 바뀐 코드를 **하나도 돌려 쓰지 않았다.** 23개를 `retired_codes`
로 내리고 새 코드를 만들었다. 내린 코드는 어떤 Catalog 에서도 다시 서지
않고(`campus:check`), 그 코드로 적힌 줄은 담당자 화면에서
`전기공학과 (지난 등록부 자리)` 처럼 **무엇이었는지**로 읽힌다.

| 확인 | 결과 |
|---|---|
| 내린 코드가 다시 선 자리 | 0 (검사가 센다) |
| 내린 코드마다 무엇이었고 왜 내렸는지 | 23/23 적혀 있다 |
| 지난 코드로 적힌 응시 줄이 집계에서 제 줄로 서는가 | 실제 DB 로 확인 |
| 지난 코드가 살아 있는 자리로 읽히는가 | 읽히지 않는다 |
| 이 기계의 응시 줄 가운데 학교 맥락이 적힌 줄 | **0건** (165건 전부 비어 있다) |

**운영 DB 는 보지 못했다.** 다만 구조로 말할 수 있다: 응시 줄에 학교 맥락이
적히는 길은 `openAttempt` 하나이고, 그 자리가 **지금 팔 수 있는 Core** 가
아니면 맥락을 통째로 버린다. 배재대의 고르는 자리는 지금까지 한 번도
`검사 가능` 이었던 적이 없으므로 운영에도 그 코드로 적힌 줄이 생길 수
없었다. **DB 마이그레이션을 하지 않았고 스키마를 한 줄도 바꾸지 않았다.**

## H. `recompute.ts:377`

**까닭.** `autoRecompute()` 의 `catch` 안에서 줄을 닫는 `finish()` 가
`.catch(() => undefined)` 로 싸여 있다. 재분석은 `MUST FAIL` 구역이라 삼키는
줄을 허락하지 않는다.

**무엇이 걸리는가.** 줄 닫기가 실패하면 그 줄이 `running` 으로 남아 화면이
`실패, 다시 시도` 대신 `돌고 있습니다` 로 선다.

**얼마나 가는가.** `claim()` 이 5분 지난 `running` 줄을 다시 집는다. **길어야
5분이고 저절로 풀린다.**

**검사 결과에 닿는가. 닿지 않는다.** 재분석은 `v3_snapshots` 에 한 줄도 쓰지
않는다. 고치는 일은 재분석 동작을 건드리므로 따로 승인받고 한다.
