# 전공 공통 엔진 세 자리와 전기전자 검토 준비

이 회차는 전공을 하나 더 만들지 않았습니다. 전기전자 Core 를 만들면서
드러난 **전공 공통 엔진 문제**를 닫고, 전기전자를 전공자 검토 상태로
고정한 것이 전부입니다. 다음 Core 제작은 이 다음입니다.

## A. 고친 세 자리

세 자리가 **같은 종류의 탈**입니다. 한 Core 의 자료나 한 Core 를
가정한 조건이 공용 층에 적혀 있었고, 다음 Core 가 그것을 조용히
물려받았습니다. 기계공학 하나만 팔 때는 셋 다 보이지 않습니다.

| 자리 | 무엇이 틀렸나 | 누가 영향을 받나 |
|---|---|---|
| `result/build.ts` `actionsOf` | 할 일이 0개인 결과가 나갔다 | 전 전공 선별 등급 |
| `scoring/engine.ts` 판본 기록 | 전기전자 응시에 기계공학 은행 판본이 적혔다 | 전기전자 응시 기록 |
| `result/text.ko.ts` `CHAIN_KO` | 전기전자 결과지에 기계공학 작성 차례가 나갔다 | 전기전자 응시자가 읽는 글 |

### A-1. 할 일이 0개인 결과

마지막 그물이 `!s.focus.length && !out.length` 였습니다. 먼저 볼 영역이
**있으면** 그 그물에 걸리지 않으므로, 선별 네 축을 다 확인한 선별 등급
응시자가 백 문항 가까이 풀고 다음에 할 일을 한 줄도 받지 못했습니다.
빈자리는 심화를 연 영역에서만 세는데 선별 등급은 깊게 묻지 않아 0이고,
스냅샷의 `next` 도 비고, 정리 묶음은 선별 등급에서 돌지 않습니다.

**전기전자 때문이 아닙니다.** 같은 응답을 기계공학 Core 로 돌려도 같습니다.

```
고치기 전  ME_CORE_V3 · P04 · BASIC — focus=[TD01,TD02] gaps=0 actions=0
고친 뒤    ME_CORE_V3 · P04 · BASIC — focus=[TD01,TD02] gaps=0 actions=1
                                      acts=[WRITE_UP@TD01]
```

기계공학 사람 열두 벌에 그 처지의 벌이 없어서 그쪽에서 드러나지 않았습니다.

조건을 `!out.length` 로 바꾸고, 무엇을 적을지는 **이미 관찰된 것**이
정합니다. 네 가지를 하지 않습니다.

- 점수를 새로 만들지 않습니다
- 강점이나 적합도를 말하지 않습니다
- 없는 빈자리를 지어내지 않습니다
- 이미 확인된 영역을 억지로 부족하다고 적지 않습니다

확인된 판단이 있는 영역이 `focus` 에 있으면 그 근거를 설명할 문장으로
만드는 일(`WRITE_UP`)이고, 하나도 없으면 전과 같이 `EXPLORE_BROADLY`
입니다. **자유문장 엔진을 더하지 않았습니다**: 문장은 `text.ko.ts` 의
기존 `WRITE_UP` 이 그대로 듭니다. 먼저 볼 영역이 없는 사람은 옛 가지로
내려가므로 결과가 전과 같습니다.

### A-2. 응시 기록의 문항 은행 판본

`scoring/version.ts` 의 `ITEM_BANK_VERSION` 이 전역 상수 하나였습니다.
그래서 전기전자 응시의 스냅샷과 `v3_attempts` 줄이
`ME_V3_ITEM_BANK_V2.5` 를 적었습니다. 판정에는 들어가지 않습니다(축
수준과 묶음은 그 Core 의 은행과 영역 사전만 읽습니다). 틀리는 것은
**되짚을 때 읽는 이름표**이고, 끝난 뒤에는 되물을 수 없습니다.

적는 자리를 `bankVersionOf(core)` 하나로 모았습니다. 적지 않은 은행은
조용히 넘기지 않고 그 자리에서 멈춥니다. 기본값을 두면 그 기본값이 다시
남의 판본이 됩니다.

`v3_attempts` 의 `assessment_version` 도 같은 탈이었습니다. `core_code`
를 SQL 안에서 정하고 판본은 전역 상수로 적어서, 한 줄 안에서 두 칸이
서로 다른 Core 를 가리켰습니다. Core 를 정하는 자리와 판본을 적는
자리를 하나로 모았습니다.

**판본 이름은 기존 convention 을 따릅니다.** 새 체계를 만들지 않았습니다.

```
ME_CORE_V3  검사 ME_V3_2  →  ME_V3_ITEM_BANK_V2.5
EE_CORE_V1  검사 EE_V1    →  EE_V1_ITEM_BANK_V1
```

전기전자 쪽 이름이 `EE_ITEM_BANK_V1` 이었던 것을 기계공학과 같은 모양
(`검사 판본 머리 + _ITEM_BANK_ + 판본`)으로 맞췄습니다. 문항은 한 줄도
바뀌지 않았고 응시한 사람이 없습니다.

### A-3. 기계공학 작성 차례가 전기전자 결과지에

검토 자료를 만들다 드러났습니다. 선별 등급 결과 예시의 할 일에
`공차와 체결 결정 → 도면 → 시작품 확인` 이 적혔습니다.

사례를 적는 차례 표가 **영역 코드만으로** 적혀 있었습니다. 그런데 영역
코드는 Core 안에서만 뜻이 있습니다.

| 코드 | 기계공학 | 전기전자 |
|---|---|---|
| TD01 | 기계설계 | 아날로그 회로 설계 |
| TD10 | 품질·신뢰성 | 에너지·신재생 시스템 |

그래서 전기전자의 에너지·신재생 영역에 품질관리 차례가 섰습니다. 전공자가
읽으면 그 자리에서 틀린 것이 보이고, 읽는 학생은 자기 전공의 말이 아님을
알아챌 뿐입니다.

표를 `result/chains.ts` 로 옮겨 **Core 를 열쇠로** 두었습니다. 문장 층은
할 일에 담겨 온 차례를 읽기만 합니다. 전기전자 열두 영역의 차례는 그
Core 의 업무 흐름에서 뽑았습니다(받는 입력 → 먼저 정하는 것 → 쓰는 방법
→ 내놓는 산출물 → 무엇과 견주는가).

```
전기전자 TD01  요구 신호와 전원 조건 → 회로 구조와 소자 선정
               → 동작점과 잡음 예산 → 회로도와 설계 계산서
               → 시작 보드 측정 대조
```

돌아오지 못하게 `v3:extend` 의 `core 를 모르게 짠 파일` 목록에
`text.ko.ts` 를 더했습니다. 그 목록은 `me-v3-` 와 `ME_CORE` 와 `TD0x` 를
본문에서 찾습니다.

## B. 기계공학이 읽는 글은 한 글자도 바뀌지 않았습니다

사람 열두 벌 × 등급 셋 × Core 둘을 돌려 그려진 한국어(머리글 · 빈자리 ·
할 일)를 글자로 견줬습니다.

```
기계공학 309줄  글자까지 같다
전기전자         새 할 일 둘 + 작성 차례가 전기전자 것으로 바뀜
```

모델 자체도 판본 칸을 뺀 지문으로 견주면 일흔두 벌 가운데 달라진 것이
`actions=0` 이던 둘뿐입니다.

않았고 화면 markup 과 자리가 그대로입니다.

## D. 스냅샷 provenance

응시 하나를 되짚는 데 필요한 여섯 칸이 전부 적힙니다.

| 칸 | 어디서 오나 |
|---|---|
| `core_code` | 그 사람이 고른 자리 |
| `specialization` | 갈래. 없으면 `null` |
| `item_bank_version` | 그 Core 의 은행이 적은 값 |
| `scoring_version` | 판단 규칙 |
| `result_model_version` | 결과 모델 |
| `assessment_ui_version` | 읽은 검사 화면 |

`core_code` 와 `core_version` 을 따로 둔 까닭은 저쪽이 채점이 읽은
Core 이고 이쪽이 그 사람이 고른 자리이기 때문입니다. 둘이 어긋나면
어느 한쪽이 거짓이므로 검사가 같은지 셉니다. 갈래를 비워 두지 않고
`null` 로 적는 까닭은, 칸이 아예 없는 것과 갈래 없이 응시한 것이 되짚을
때 구별되지 않기 때문입니다.

## E. 두 Core 가 섞이지 않습니다

`npm run v3:provenance` 가 실제 DB 에 줄을 넣어 봅니다. 번갈아 여는
까닭은 같은 Core 를 잇따라 열면 섞이는 것을 볼 수 없기 때문입니다.

```
ME → ME 은행 · ME 검사 판본
EE → EE 은행 · EE 검사 판본
ME → EE → ME → EE  네 줄 전부 짝이 맞는다
```

닫아 둔 Core 는 학교 맥락이 통째로 버려지는 것이 설계이므로, 이 절은
그 칸을 잠시 열고 **반드시 되돌립니다.** `finally` 가 되돌리고 등록부
지문을 견주고 전기전자가 다시 닫혔는지 확인합니다. 검사가 넣은 사람과
응시 줄은 끝에서 지웁니다.

## F. 검사가 실제로 거르는지 되돌려 확인했습니다

```
fallback 을 옛 조건으로  → 걸림  할 일이 0개인 결과가 없다
                                 EE/P04/BASIC · EE/P05/BASIC
판본을 전역 상수로       → 걸림  판본을 적는 길이 전역 상수를 읽지 않는다
                          걸림  응시마다 그 Core 의 은행 판본이 적힌다
```

거짓 경보를 내는 검사는 그 다음부터 아무도 보지 않습니다. 그래서 고친
자리를 되돌려 실제로 걸리는 것까지 봤습니다.

## H. 전기전자 검토 상태

```
status             building
maturity           READY_FOR_DOMAIN_REVIEW
open_to_students   false
```

`READY_FOR_REVIEW` 와 따로 둔 까닭이 있습니다. 앞엣것은 `누군가 봐야
한다` 까지이고 뒤엣것은 **누가 무엇을 봐야 하는지가 정해져 있습니다**:
그 전공 전문가와 현직자가 읽을 묶음이 만들어져 있고 판정 칸이 비어 있는
상태입니다. 한 칸으로 묶으면 `검토를 부탁할 자료가 아직 없다` 와
`자료는 있고 답을 기다린다` 가 구별되지 않고, 그러면 아무도 검토를
시작하지 않습니다.

**이 글자는 손님 화면에 서지 않습니다.** 학생에게 할 말은 `지금 열려
있는가` 하나이고 그것은 `status` 와 `open_to_students` 가 정합니다.
`v3:majors` 가 `src/app` 과 `src/components` 에서 성숙도 값을 세고,
운영 화면은 그 값을 읽어야 하는 자리라 보지 않습니다.

## I. 검토 묶음

```
docs/metri/EE_CORE_V1_REVIEW.md    1,220줄
docs/metri/EE_CORE_V1_REVIEW.csv     313항목
npm run ee:review                  다시 만드는 명령
```

손으로 적지 않는 까닭은 문면을 고친 날 검토표가 조용히 옛 문장을 들고
있기 때문입니다. 사람이 적는 자리는 원본 JSON 이고 여기서 나오는 것은
생성물입니다. 판정 칸은 비워 두고 검토자가 채웁니다.

담긴 것은 이렇습니다.

| 절 | 담긴 것 |
|---|---|
| 머리말 | 표시 네 가지 · 묻는 열 가지 · 보기 넷의 뜻 |
| 1 | 기술영역 12개 · 필수 축 · 대표 문항 셋 · 수행과 소유 조건 · 근거 항목 |
| 2 | 산업팩 8개 · 요구 · 보는 판단 · 대표 문항과 쉬운 말 풀이 · 현장 용어 · 빈자리 문장 |
| 3 | 역할팩 8개 · 확정하는 것 · 보는 영역과 축 · 대표 문항 · 산출물 예시 · 옆 역할과 갈리는 자리 |
| 4 | 결과 예시 셋(선별 · 견주기 · 번역) |

결과 예시는 **실제 엔진이 낸 것**입니다. 손으로 적은 예시가 아닙니다.

## J. 이번에 하지 않은 것

학생 공개와 결제 연결과 규준과 백분위와 적합도 비율과 `검증된 검사`
표현과 다음 Core 제작과 지역 자료와 Track 은 건드리지 않았습니다.
실제 응답으로 신뢰도와 타당도를 재지 않았으므로 어느 자리에서도
`검증된 검사` 로 적지 않습니다.

운영 배포본을 밖에서 열지 못했습니다. 작업 환경의 네트워크 정책이
`app.careermatri.com` 의 HTTPS 를 막습니다. 위의 모든 결과는 이 기계에서
운영과 같은 배치로 띄워 돌린 것입니다. DB 스키마를 한 줄도 바꾸지
않았으므로 마이그레이션은 필요 없고, 고친 것이 전부 이미지 안으로
들어가는 파일이라 재배포가 먼저입니다.
