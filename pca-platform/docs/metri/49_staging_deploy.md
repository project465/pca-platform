# 49. 공개 전 시험 배포

> 밖에서 브라우저로 열어 끝까지 눌러 보기 위한 배포다. **손님에게 열지
> 않는다**: 결제 대행사 · 메일 · 사업자 표시가 아직 없다.

## 0. 코드가 할 수 있는 데까지

서버 · 도메인 · DB 계정은 **밖에서 정해진다.** 그래서 이번에 만든 것은
그것이 정해졌을 때 **한 번에 서게 하는 것**과, 공개 전 배포본이 운영으로
오해되지 않게 막는 것이다.

```
deploy/docker-compose.staging.yml   앱 · DB · HTTPS · 밤 당번
deploy/Caddyfile                    app.careermatri.com 하나만 받는다
.env.staging.example                값을 지어내지 않은 틀
scripts/dev-setup.sh                빈 DB 에서 한 번에
scripts/staging-check.ts            공개 전답게 섰는가 8가지
deploy/README.md                    순서
```

## 1. `NODE_ENV` 로 운영을 판단하지 않는다

가짜 결제를 막는 자리가 `NODE_ENV === "production"` 이었다. **그 값은
빌드가 최적화됐다는 뜻**이지 손님이 돈을 내는 자리라는 뜻이 아니다.
staging 도 똑같이 production 으로 빌드된다. 그래서 공개 전 배포본을
띄우는 순간 결제가 막히거나, 막히지 않게 하려고 `ALLOW_MOCK_PAYMENTS=yes`
를 넣게 되는데 **그 한 줄이 운영 설정에 섞여 들어가면 돈을 안 받고
이용권이 나간다.**

판단을 `APP_ENV` 로 옮기고 **문을 없앴다**(`src/lib/env.ts`).

```
dev         손에서 띄운 것
staging     밖에서 열리지만 손님에게 열지 않은 것. 가짜 결제를 쓴다
production  손님이 돈을 내는 자리. 가짜 결제가 어떤 값으로도 안 열린다
```

**비어 있으면 dev 다.** 모르는 배포본을 운영으로 보면 아무도 못 사고
그날 바로 드러나지만, staging 으로 보면 운영에서 가짜 결제가 열린 채로
몇 달이 간다. `launch:check` 가 옛 열쇠를 꽂아 두고도 거절하는지를 센다.

## 2. 자물쇠는 주소를 숨기는 것이 아니다

`STAGING_BASIC_AUTH` 가 있으면 미들웨어가 전부 막는다(`/api/health` 만
뺀다. 앞단이 살아 있는지 묻는 자리라 열쇠를 들고 다니지 않는다).

**주소를 아는 사람만 막는 것은 자물쇠가 아니다.** 검색엔진이 먼저
찾아내고, 찾아낸 자리에 가짜 결제가 열려 있다. 그래서 응답에
`X-Robots-Tag: noindex` 를 앱과 앞단 양쪽에서 붙인다.

## 3. 공개 전이라는 것을 쪽마다 적는다

공개 전 배포본은 손님 화면과 똑같이 생겼다. 그래서 눌러 본 사람이
"결제가 됐다" 를 진짜로 읽고 나중에 그 주문을 찾는다. 아래 띠에
**가짜로 받고 있다**는 것을 적는다(`StagingMark`). 운영에서는 아무것도
그리지 않는다.

## 4. 공개 전에는 이 배포본의 주소가 먼저다

메일 링크와 결제 콜백은 `site_configs` 의 정규 주소를 쓴다. 그런데 그
주소는 소개 사이트가 설 자리(`careermatri.co.kr` · `careermatri.com`)이고
공개 전에는 거기에 플랫폼이 없다. 그 주소로 보내면 눌러 본 사람이 빈
도메인에 떨어진다. **실제로 가짜 결제가 그렇게 끊겼다.**

`APP_ENV=staging` 이면 `PLATFORM_URL` 이 먼저다.

## 5. 아직 밖에서 정해져야 하는 것

서버 · 관리형 Postgres · 결과지 파일 저장 · DNS 한 줄. 고르는 기준과
값은 `docs/metri/45_owner_decisions.md` 와 이번 보고에 적었다. **임의로
업체를 고르지 않는다**: 한 번 고르면 옮기는 데 드는 값이 고르는 데 드는
값보다 훨씬 크다.
