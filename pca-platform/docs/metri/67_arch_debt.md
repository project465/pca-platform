# POST ME-V3 PILOT ARCHITECTURE DEBT

Wave 0 이 끝난 뒤에 갚을 빚이다. **지금 갚지 않는다**: 파일럿이 재려는
것은 기계공학 V3 의 문항과 결과이고, 그것을 재는 동안 그 아래 층을
일반화하면 파일럿이 재는 제품이 중간에 바뀐다.

여기 적는 까닭은 하나다. 적어 두지 않으면 두 번째 전공을 여는 날 그
자리에서 처음 발견하게 되고, 그날은 이미 일정이 걸려 있다.

---

## 1. `platform.ts` 와 `recompute.ts` 가 기계공학 하나에 묶여 있다

**무엇이 묶여 있는가.**

`src/lib/me-v3/platform.ts` 는 `export const CORE = "ME_CORE_V3"` 를
상수로 들고 열네 자리에서 그 값을 쓴다. `career_profiles` ·
`v3_actions` · `v3_experiences` 를 읽고 쓰는 질의가 전부 그 상수를
`core_code` 자리에 넣는다. `src/lib/me-v3/recompute.ts` 도 같다.

그래서 지금 구조는 **한 사람이 전공 Core 하나만 가진다**는 가정 위에
서 있다. 표는 그렇지 않다: `career_profiles` 의 유일 열쇠가
`(user_id, core_code)` 라서 DB 는 이미 사람 하나에 Core 여럿을 받는다.
**스키마가 허용하는 것을 코드가 막고 있는 자리**다.

**왜 지금 고치지 않는가.**

열린 Core 가 하나라서 지금은 틀린 답을 내지 않는다. 그리고 이 층을
일반화하려면 대시보드와 경험 추가와 재분석과 Gap 화면이 **어느 Core 의
이야기인지**를 화면에서 가려야 하는데, 그것은 정보 구조를 바꾸는 일이고
기준선 동결 아래에서 할 일이 아니다.

**두 번째 전공을 여는 날 무엇이 먼저 깨지는가.**

| 자리 | 지금 | 두 전공이 열리면 |
|---|---|---|
| `profileOf(userId)` | Core 하나를 집는다 | 어느 Core 인지 받아야 한다 |
| `latestResult(userId)` | 가장 최근 스냅샷 하나 | 전공마다 따로 돌려줘야 한다 |
| `resultHistory(userId)` | 지금 값 한 줄 + 스냅샷 | 전공으로 묶어 적어야 한다 |
| `addExperience` | `core_code` 를 상수로 적는다 | 그 경험이 어느 전공의 일인지 받아야 한다 |
| `previewRecompute` | 한 Core 의 축만 센다 | 전공마다 따로 세고 섞지 않아야 한다 |
| `/me` 대시보드 | 전공 이름이 없다 | 전공을 고르는 자리가 필요하다 |

**갚는 순서.** 함수 서명에 `coreCode` 를 받는 것이 먼저고, 화면에서 전공을
고르는 자리가 그다음이다. 거꾸로 하면 화면이 고를 수 있는데 아래가 못
받는 상태가 한동안 남는다.

---

## 2. 경험이 전공을 건너 쓰이지 않는다

`v3_experiences` 에 `core_code` 가 붙어 있어서, 전기전자 Core 가 열리면
같은 캡스톤을 두 번 적게 된다. **사람은 하나이고 경험도 하나다.**

ME_V2 와 ME_V1 은 경험 표를 공유해서 이 문제가 없었다. V3 에서 Core 를
붙인 것은 영역 코드(`td_codes`)가 Core 마다 다르기 때문이다. 갚는 길은
경험 줄을 Core 에서 떼고 **(Core · 영역) 짝을 따로 두는 표**로 옮기는
것이다.

---

## 3. 지역 층에 자료가 한 줄도 없다

`region_industry` · `industry_td_demand` · `org_registry` 가 스키마만
있고 줄이 없다. 공고 자료는 저작권과 이용약관 검토 전이다.
**짐작으로 채우지 않는다**: 기관 수가 근거처럼 읽히고 그걸 믿고 움직이는
사람이 생긴다.

---

## 4. 자동 재분석이 사람 없이 돌지 않는다

`career_events` 에 할 일이 쌓이고 사람이 `/me/recompute` 에서 누를 때만
돈다. 저장과 동시에 돌리지 않은 것은 일부러다(계산이 깨진 날 저장까지
막히지 않게, 그리고 무엇이 달라지는지 먼저 보고 누르게). 하지만
`Track` 이 파는 것은 자동 재계산이라, 그 상품을 켜는 날 당번이 필요하다.

---

## 5. 영어판이 한 줄도 없다

결과 모델은 한국어를 들고 있지 않고 번역표(`text.ko.ts`)가 따로라
구조는 서 있다. 없는 것은 **영어 문면**이다. 문항 369개와 결과지 문장과
화면 카피 전부다.

---

## 6. 검사의 구멍을 메운 자리 (이번 회차에 갚았다)

`scripts/db-migration-check.ts` 의 칸 이름 추출이 **쉼표 앞에 낱말 경계를
요구하고 있었다.** `SET state='done', updated_at=now()` 처럼 앞엣것이
따옴표면 따옴표와 쉼표가 둘 다 낱말이 아니라서 경계가 없고, 그 쉼표 뒤의
칸이 통째로 안 세어졌다. `v3_actions` 에 없는 `updated_at` 을 쓰는 줄이
그렇게 이 검사를 지나갔고, 재분석을 누르는 자리에서 터졌다.

낱말 경계를 낱말인 쪽에만 붙이고 다시 돌리니 세는 칸이 508개에서
523개로 늘었다. 되돌려 보고 그 줄을 집어내는 것까지 확인했다.

**같은 모양의 빚이 또 있을 수 있다.** 이 검사가 보는 것은 백틱 안의 SQL
이라, 문자열을 이어 붙여 만드는 질의는 아직 보지 못한다.
