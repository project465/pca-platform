# Phase 2.2 — 파는 제품으로

받은 규격 `CAREERMATRI_PHASE2_2_COMMERCIAL_LAUNCH`. **다음 이정표는
기능이 아니라 "믿을 수 있는 첫 유료 손님" 이다.**

## 0. 한 줄

사기 전에 읽을 자리와 받은 뒤에 막혔을 때 빠져나올 자리를 만들었다.
**켜는 것을 막는 열아홉 가지는 전부 우리 밖에서 정해진다**(가격 · 결제
대행사 · 사업자 등록 · 도메인 · 메일 대행사 · 복구 시험).

```bash
npm run launch:check   # 끝낸 것 30가지 · 막힌 것 19가지
npm run launch:e2e     # 결제 → 환불 → 메일 두 언어 33가지
```

## 1. 새로 생긴 자리

| 어디 | 무엇 |
|---|---|
| `/product` | 상품 쪽 열세 절. 사기 전에 읽는다 |
| `/sample` | 견본 결과지. **실제 엔진으로 그린다** |
| `/support` | 주문 번호 · 참조 번호 · 환불 요청 · 메일 확인 · 비밀번호 |
| `/pilot/[id]` | 파일럿 열 문항 |

| `/admin/incidents` | 결제 · 이용권 · 멈춘 응시 · 결과 · PDF · 메일 |
| `/admin/refunds` | 요청과 그때의 판정, 승인과 거절 |
| `/admin/funnel` | 방문에서 PDF 까지와 파일럿 |

## 2. 작업 중 드러난 진짜 탈 넷

### ① 거래 메일 세 통이 조용히 안 나가고 있었다

규격 §14 가 요구한 여섯 통 가운데 결제 확인 · 환불 접수 · 환불 처리가
없었다. 코드에 종류를 늘리고 문면까지 썼는데 **한 통도 쌓이지 않았다.**

까닭은 `outbox.kind` 의 CHECK 였다. 네 가지만 허용하고 있어서 INSERT 가
거절됐고, `enqueue()` 는 실패해도 던지지 않는다. 돈길에 메일을 끼우지
않으려고 일부러 그렇게 두었는데, 그 설계가 **이 종류의 탈을 조용하게**
만든다. 제약을 늘리고, `launch:check` 가 이제 코드의 종류를 DB 제약과
대조한다.

**새로 넣은 검사가 새로 넣은 코드를 잡았다.** 런칭 E2E 를 안 썼으면
결제 확인 메일 없이 팔기 시작했을 것이다.

### ② PDF 가 없는데 내려받는 단추가 서 있었다

결과지 쪽이 스냅샷만 보고 단추를 그렸다. PDF 만들기가 깨진 날에도 단추가
서고, 누르면 404 가 떴다. **웹 결과지는 그대로 열려 있는데** 받은 사람
쪽에서는 제품이 깨진 것으로 보인다.

이제 PDF 가 없으면 그 자리에 다시 만드는 쪽으로 보내고, 왜 없는지를
적는다(규격 §16: PDF 가 깨져도 웹 결과지는 열려 있어야 한다).

### ③ 비밀번호 재설정 메일이 아예 없었다

`TODO: 메일 발송 연결` 로 남아 있었고 운영에서는 아무것도 하지 않았다.
개인 결제로 파는 제품에서 이것이 없으면 **비밀번호를 잊은 사람은 끝이다.**

붙이면서 대기열에 넣지 않았다. 링크에 한 번 쓰는 열쇠가 들어 있어서
`outbox.payload` 에 적으면 DB 가 새는 순간 남의 계정이 되고, 보낸 뒤에도
그 줄이 표에 남는다. 그래서 `sendNow()` 로 **그 자리에서 보내고 아무것도
적지 않는다.** 메일 주소 확인도 같은 길이다.

### ④ 검사가 지어낸 값을 DB 에 남겼다

런칭 E2E 가 값이 승인되지 않은 상품을 잠깐 29,000원으로 켜고 끝에
되돌리는데, 켜는 줄을 `try` 바깥에 두었다가 뒤의 줄에서 터졌다. **29,000
원이 DB 에 남았다.** 지어낸 값이 남으면 그것이 어느 날 그대로 결제된다.
켜는 것도 `finally` 가 지키는 안으로 옮겼다.

## 3. 견본을 손으로 만들지 않았다

사기 전에 보여 주는 결과지(`/sample`)가 **산 사람의 결과지와 같은 한
벌**(`PCAV2Report.render`)로 그려진다. 가짜 응시자 하나를 지어 놓고
`node scripts/sample-report.mjs` 가 그 결과 객체를 떠 둔다.

```
sample.ko.json   7쪽
sample.en.json   7쪽
```

**따로 적어 두면 제품을 고친 날 견본만 옛것으로 남고**, 그 차이를 아무도
세지 않는다. 담긴 값은 전부 지어낸 것이라 로그인 없이 열린다(규격 §7:
실제 응시자의 자료를 쓰지 않는다).

## 4. 등급을 문항 수로 팔지 않는다

규격 §4 와 §24 가 같은 것을 다르게 말한다. 48 · 68 · 92 를 앞세우면 사는
쪽에서 비싼 등급을 "문항이 더 많은 것" 으로 읽고, 그러면 같은 값을 더 낼
이유가 없다.

받는 것을 `src/lib/tiers.ts` 한 곳에 적고 상품 쪽과 가격표가 그것을
읽는다. 문항 수는 작은 글씨로 내렸다.

```
BASIC      먼저 볼 방향
STANDARD   직무를 견주는 깊이
PRO        증거 구조와 실행 전략
```

그리고 **등급이 서로 구별되는지를 검사가 센다**(`tiersDistinct`). 아래
등급에 있는 것 한 줄을 빼고도 새로 붙는 것이 셋 이상 없으면 걸린다.

## 5. 지원을 창업자 한 사람에 매달지 않았다

규격 §15 의 요지는 "창업자가 DB 를 열어 보는 것으로 지원을 대신하지
말라" 다. 그래서 `/support` 는 **본인이 직접 보는 것부터** 적는다.

| 보이는 것 | 왜 |
|---|---|
| 주문 번호와 결제 상태 | 문의할 때 적을 번호가 자기 화면에 있다 |
| 막힌 것의 참조 번호 | 운영자가 그 번호로 그 사건을 바로 찾는다 |
| 환불 요청과 그 상태 | 규칙을 약관에만 적어 두면 메일을 쓸 줄 아는 사람만 쓴다 |
| 비밀번호 복구 | 개인 결제 제품에서 이것이 없으면 끝이다 |
| 두 번 결제하지 말라는 안내 | 두 번 결제되면 우리가 돌려줘야 한다 |

**남의 것은 보이지 않는다.** 주문 번호를 주소에 넣어도 `user_id` 로
걸러 읽는다. 추측하기 어려운 번호는 막는 것이 아니다.

## 6. 환불은 판정과 기록과 집행이 셋이다

판정은 이미 `refund.ts` 한 곳에서 했다. 없던 것은 **요청이 들어온
사건**이다.

```
요청 → 그때의 판정을 박아 둔다 → 운영자 결정 → 집행
```

**요청 시점의 판정을 값으로 적는다.** 응시 상태와 결과지 상태는 시간이
지나면 바뀌고, 요청한 다음 날 응시를 시작했다고 해서 어제의 권리가
사라지면 안 된다. 승인할 때는 지금 규칙으로 한 번 더 본다.

**승인이 곧 송금이 아니다.** `approved`(돌려주기로 정했다)와
`refunded`(실제로 나갔다)를 나눠 두었다. 하나로 두면 심사 전에 누른
'승인' 이 "이미 받으셨습니다" 로 읽힌다.

**자유입력을 받지 않는다.** 사유는 다섯 가지 가운데 고르고, 사정은 지원
메일로 온다. 거래 기록은 5년 남으므로 그 표에 사람의 서술을 담으면
파기가 반쪽이 된다.

## 7. 퍼널은 표만 있고 아무도 쓰지 않았다

`analytics_events` 가 처음부터 있었는데 적는 코드가 한 줄도 없었다. 그래서
지금까지 "몇 명이 가격표를 보고 몇 명이 샀는가" 에 답할 수 없었다.

```
방문 → 가격표 → 결제 시작 → 결제 확정 → 응시 시작 → 응시 완료
     → 경험 입력 → 결과지 열람 → PDF
```

**사람으로 센다, 사건으로 세지 않는다.** 가격표를 다섯 번 새로 고친
사람이 다섯 명으로 세어지면 전환율이 바닥으로 보인다. 로그인 전은 쿠키
하나(`cm_a`)로 세고, **IP 와 User-Agent 를 함께 적지 않는다**: 그 둘이
붙으면 그 쿠키가 개인정보가 된다.

**적는 열쇠를 좁혀 두었다.** 등급 · 상품 · 시장 · 언어 · 분류된 사유
다섯 개뿐이다. 경험 본문이 이 표에 들어가면 거래 분석을 보는 사람이
응시자의 서술을 읽게 된다.

## 8. 백업은 복구해 보기 전까지 완료가 아니다

`deploy/backup.sh` 가 받고, 받은 자리에서 `pg_restore --list` 로 읽어
본다. 열 수 없는 파일은 백업이 아니다.

복구 절차는 `docs/metri/44_production_infra.md` 5절에 있고, **운영 DB 에
바로 붓지 않는다**: 빈 DB 를 만들어 거기에 붓고 돈과 사람이 들어 있는 표를
센 뒤 결과지 한 장이 실제로 열리는지 본다.

한 번 해 본 날짜를 `DB_BACKUP_VERIFIED_AT` 에 적어야 `launch:check` 가
그 줄을 통과시키고, 90일이 지나면 `/admin/launch` 가 WARNING 으로 돌린다.
스키마가 바뀌면 복구 절차도 같이 바뀌므로 한 번 하고 끝나는 일이 아니다.

## 9. 켜는 것을 막는 것

열아홉 가지이고 전부 우리 밖에서 정해진다. 한 장으로는
`docs/metri/45_owner_decisions.md`.

| 무엇 | 누가 정하는가 |
|---|---|
| 여섯 등급의 값과 글로벌 통화 | 사업 결정 |
| 국내 PG · 해외 PG | 심사 · 사업 결정 |
| 사업자 표시 일곱 칸 | 사업자 등록 |
| 지원 메일 주소 | 사업 결정 |
| 메일 대행사 | 운영 담당 |
| 도메인 둘 | 도메인 구매 |
| 영문 약관 본문 | 법률 검토·번역 |
| 복구 시험 | 운영 담당 |

## 10. 소프트 런칭 순서

규격 §27·§28 을 그대로 따른다.

1. 한국 B2C 먼저. `careermatri.co.kr` · 한국어 · KRW
2. 통제된 트래픽으로 열고 **초기 거래를 한 건씩 본다**
3. 20~50명 파일럿. 기계공학만, 학부부터 박사후연구원까지
4. 퍼널이 안정되기 전에 유료 광고를 돌리지 않는다
5. 글로벌은 영어 품질 승인 · 해외 PG · 영문 약관 승인 뒤에

**처음 20~50명은 어디서 오는가.** 지금 손에 있는 경로는 학과 계약이다.
기계공학과 취업지원처 한 곳과 이야기해서 그 학과 학생에게 열어 보는
쪽이, 광고로 낯선 사람 쉰 명을 데려오는 것보다 **답을 빨리 준다**:
같은 전공이고 같은 학년대라 결과지가 읽히는지를 바로 비교할 수 있다.
다만 그 경로는 B2B 가격으로 들어오므로, **지불의향은 따로 물어야 한다**
(파일럿 7·8번 문항이 그 자리다).

## 11. 아직 아닌 것

- 운영 인프라에 올리지 않았다. 이 컨테이너는 세션이 끝나면 사라진다
- 실제 PG 로 한 건도 결제하지 않았다. 심사 전이다
- 메일을 한 통도 보내지 않았다. 대행사가 없다
- 파일럿 응답이 0건이다. 도구만 서 있다
- 재응시와 결과지 갱신 규칙이 없다. FAQ 에 "정해지지 않았다" 로 적었다
