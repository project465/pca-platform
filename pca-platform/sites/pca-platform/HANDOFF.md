## 2. 원안과 다르게 구현한 것 — 반드시 읽어주세요

`assets/engine.js`의 `CONFIG` 한 곳에 모아두었고, 값만 바꾸면 전부 원안으로 돌아갑니다.
바꾼 이유는 아래와 같습니다. **되돌릴지 여부는 제품 결정이므로 확인이 필요합니다.**

### (1) FIT 공식 — `fitMode: 'shape'` (원안 `'absdiff'`)

원안은 `FIT = 100 − 8개 차원 평균절대차`입니다.
그런데 직무 벡터의 평균이 72.5(기계설계)~83.6(공정기술)으로 11점 범위에 몰려 있어서,
이 공식은 **응답자의 전반적인 응답 높이가 순위를 결정**합니다.

시뮬레이션 결과(원안 공식):

| 응답 유형 | TOP 1 |
|---|---|
| 전부 3(중립) | 기계설계 |
| 전부 1(낮게) | 기계설계 |
| 전부 5(높게) | 기계설계 |
| 탐구/연구형 | 기계설계 |

즉 어떤 성향이든 기계설계가 1위로 나옵니다.

바꾼 방식은 개인 벡터와 직무 벡터를 각각 중심화한 뒤 코사인 유사도를 0~100으로 옮긴 것입니다.
`02_Scoring_Rules` 시트에 이미 대안으로 적혀 있던 방식이고,
"FIT은 업무방식의 유사성"이라는 제품 정의와도 맞습니다.

같은 시뮬레이션(변경 후):

| 응답 유형 | TOP 1 |
|---|---|
| 현장/실행 중심 | 설비·유지보수 |
| 해석/데이터 중심 | CAE·해석 |
| 검증/품질 중심 | 품질·신뢰성 |
| 협업/기획 중심 | 기술기획·PM |
| 탐구/연구 중심 | R&D |

### (2) FUTURE 문항을 Career DNA에서 제외 — `futureInDna: false`

ME065~068은 DNA 가중치를 갖는 동시에 READY의 FutureWork(25%)로도 쓰입니다.
같은 응답이 두 번 반영되어 "FIT과 READY는 분리"라는 원칙이 깨집니다.

### (3) ME087~092를 EVIDENCE에서 제외 — `applyItemsInEvidence: false`

6문항 모두 채용공고 분석·PAR 정리·포트폴리오 증명·면접 설명 등 **지원준비** 문항이고,
PRO READY의 Application Readiness(10%)에 이미 사용됩니다.
직무 수행 경험이 아니므로 Evidence 가중평균에서 뺐습니다.

### (4) CONSISTENCY 문항을 Career DNA에서 제외 — `consistencyInDna: false`

문서상 신뢰도 플래그 전용입니다. 참고로 8문항 전부 RESERVE라
현재 어느 상품에서도 출제되지 않습니다. 즉 **일관성 검증이 실제로는 작동하지 않는 상태**입니다.
Stage 4에서 출제 폼에 배정할지 결정이 필요합니다.

## 3. 아직 안 된 것 (다음 작업)

### 우선순위 1 — 서버 연동

지금은 전부 브라우저에서 계산하고 `localStorage`에 저장합니다. 그래서

- 가중치·직무 매트릭스가 프론트에 노출됩니다
  (Stage 3 보안 기준 1·2번 위반 — 정적 호스팅의 한계)
- 기기를 바꾸면 이어서 응시할 수 없습니다
- 기관이 응시 현황을 볼 수 없습니다
- 결제 entitlement 검증이 없습니다

바꿔야 할 지점은 두 곳뿐입니다.

```
assets/app.js  →  store() / save()     : localStorage → 서버 API
assets/app.js  →  showResult() 끝부분   : window.PCA_RESULT를 서버로 POST
```

DB 스키마와 API 규격은 이미 만들어져 있습니다.
`Career_Matri_V2_0_Developer_Package.zip`의 `db_schema.sql` / `api_spec.md`,
`Career_Matri_V2_0_Stage3_Payment_Member_DB.zip`의 `01_db_schema.sql`을 그대로 쓰면 됩니다.

문항 노출을 막으려면 `GET /api/v2/assessments/{id}/questions`에서
문항 텍스트와 선택지만 내려주고 가중치는 서버에 두는 구조로 옮겨야 합니다.
그 경우 `assets/engine.js`를 서버(Node)로 옮기면 됩니다. 순수 함수라 그대로 이식됩니다.

### 우선순위 2 — 결과지 PDF

`Career_Matri_V2_0_STANDARD_PDF_Automation.zip`에 Result JSON → 24페이지 PDF 생성기가 있습니다.
`window.PCA_RESULT`의 형태를 그 스크립트의 입력 JSON 형식에 맞추는 변환 함수만 쓰면 연결됩니다.

### 우선순위 3 — 학과 확장

도구가 준비되어 있으므로 학과당 필요한 것은 두 가지입니다.

1. 해당 학과의 계산엔진 xlsx(문항 120·직무 매트릭스·Evidence 매트릭스)
2. `content/<code>.json` — 직무별 서술 콘텐츠

자세한 절차는 `README.md`의 "학과 추가하기"에 있습니다.

### 우선순위 4 — Stage 4 파일럿 검증

원본 인수인계 문서의 다음 단계입니다. 아직 시작하지 않았습니다.
문항 분포, ceiling/floor, 문항-총점 상관, 차원별 α/ω, 중복문항,
직무군 분리도, Job Matrix 보정 후보, KEEP/REVISE/DROP 자동 분석.

## 4. 검증 전에 알고 있어야 할 구조적 한계

플랫폼 버그가 아니라 문항 설계에서 오는 것들입니다.

**STANDARD의 EVIDENCE가 6문항에 의존합니다.**
ME059~064 6개뿐인데 READY의 75%를 차지합니다. 직무별 실효 문항 수는 다음과 같습니다.

| 직무 | 근거 문항 수 |
|---|---|
| R&D, 생산기술 | 6 |
| CAE·해석, 공정기술 | 5 |
| 기계설계, 품질·신뢰성, 설비·유지보수, 기술기획·PM | 4 |

4문항으로 "현재 준비도"를 점수로 제시하는 구조라 파일럿에서 신뢰도가 낮게 나올 수 있습니다.
플랫폼에서는 결과 화면에 **근거 문항 수를 함께 표시**해 두었습니다(FIT ≠ READY 섹션).

**직무 요구치가 100인 칸이 3곳 있습니다.**
품질·신뢰성 VP=100, 설비·유지보수 EXE=100, 기술기획·PM CI=100.
GAP이 구조적으로 0이 될 수 없습니다.

**QUICK → STANDARD 업그레이드 시 DNA 점수가 달라집니다.**
정규화 기준(이론적 min/max)이 문항 수에 따라 바뀌기 때문입니다.
같은 28문항 응답인데 점수가 변하므로, 업그레이드 화면에 설명이 필요합니다.
아직 넣지 않았습니다.

**정규화가 이론적 최대/최소 기준입니다.**
실제 응답자 점수가 중간대로 몰립니다. Stage 4 이후 경험적 백분위 규준으로 바꾸는 것을 권합니다.
